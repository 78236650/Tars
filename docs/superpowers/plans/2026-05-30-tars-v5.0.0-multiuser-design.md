# TARS v5.0.0 「多用户协作 + 并发底座」实施计划

> **For agentic workers:** 用 superpowers:executing-plans 或 subagent-driven-development 按 Task 逐条实施。每个 Task 做完能独立跑通、能测、能提交。遇到与现状冲突的，**以现状代码为准，先问再改**。

---

## 〇、方向校准（重要：从多租户拉回多用户）

**用户已明确决策（2026-05-30）**：

| 维度 | ❌ 不做 | ✅ 要做 |
|---|---|---|
| 隔离模型 | SaaS 多租户（多企业互相隔离） | **单组织内多用户协作**（一家港航企业，全员同池） |
| 共享边界 | 租户级隔离 | **全员共享一个组织池**（记忆/知识库/实体图谱/workflow 全员共享，仅个人会话/偏好 private） |
| 并发 | — | **直接迁 Postgres**，扛多用户持续并发写 |
| 认证 | SSO（后续再说） | **自建账号密码 + JWT** |
| 本版本范围 | workflow 可配置化、港航 Agent 实化（往后排） | **多用户 + 并发 + Postgres 三件套** |

**为什么这个方向对**：港航企业最值钱的是"组织级知识沉淀"——调度员录入的"QC-7 大梁裂纹"，船务的 Agent 必须能看到。SaaS 多租户的隔离反而是阻碍。单组织全员同池 + 个人会话私有，正好匹配。

**已确认的三点（实施硬性规则）**：

1. `tenant_id` 语义统一为 **`org_id`（单组织恒 `org_default`）**，废弃 `user_id == tenant_id`。
2. **JWT 为人类用户主路径**；API Key 保留给 `/api/invoke` 等机器集成。
3. v5.0 **In**：JWT + org 池 + Postgres；**Out**：SaaS 多 org、G3 workflow、V1 港航真工具（→ v5.1+）。

## 一、关键现状发现（已核实，决定改造范围）

逐条核对代码后：**scope / 实体图谱 / 密码哈希 / repository 层已具备基础**，但 **`memories` 缺 `user_id` 列、知识库仍按 tenant 分岛、认证仍走 API Key**，改造量中等，不是「只改 WHERE」。

| 发现 | 证据 | 含义 |
|---|---|---|
| `sessions` 已有 `user_id` + `tenant_id` | `connection.py:49-53` | 会话可按用户过滤 |
| `memories` 有 `tenant_id` + `scope`，**无 `user_id`** | `connection.py:77-88,103-105` | 当前 private 靠 **`tenant_id=user.id`** 隔离，非 user_id 字段 |
| 记忆查询 `WHERE (tenant_id=? OR scope='shared')` | `memory_repo.py:179,198,215` | shared 跨 tenant 可见，但 tenant 仍 = user.id → **组织池语义未落地** |
| `document_collections` / 知识检索全程 `tenant_id` | `api/knowledge.py`、`knowledge/access.py` | ⚠️ 知识库与记忆同样「每人一岛」，**须 T2.5 org 化** |
| `entities` / `memory_relations` **无 tenant_id/user_id** | `connection.py:442-476` | 实体图谱天然全局 = 组织池，T2.3 仅加测试 |
| Chroma 按 `{collection}_{tenant_id}` 分库 | `vectorstore/chroma_client.py:41` | tenant_id=user.id → shared 记忆语义检索跨人搜不到 |
| `users.password_hash`(PBKDF2) 已有 | `user_store.py:52-57` | 密码校验可复用 |
| `user_sessions` 表 | `user_store.py:64-71` | **仅** user↔session_id 关联，**不是** JWT refresh 表，需新表或扩字段（T1.2） |
| 认证 SSOT：`api/_auth.py` | `resolve_authenticated_principal` | 非 admin 时 `tenant_id = user.id`，**须 T1.4 一并改** |
| DB sqlite3 + repository + sql_dialect | `connection.py`、`database/repositories/` | Postgres 迁移有地基 |
| Approval/Handoff/Follow-up waiters | 进程内内存 | **多 uvicorn worker 会丢状态**，见 T3.4/T3.5 |

**核心矛盾点**：`tenant_id` 一身二用——既被当作「组织共享维度」（`scope=shared`），又被赋值为 `user.id` 当「用户私有维度」。多用户化 = **拆语义 + 补列 + 统一向量库/知识库**：

```
org_id (原 tenant_id)  →  恒为 "org_default"，组织共享池边界
user_id                →  个人私有（memories 需新增列；sessions/core_memory 已有或待改）
scope                  →  shared = 组织池全员可见；private = 仅该 user_id
```

改造后记忆过滤：`WHERE tenant_id='org_default' AND (scope='shared' OR user_id=?)`

**数据回填规则（T2.1 迁移）**：

- 原 `tenant_id=<旧用户id>` 且 `scope='private'` → `user_id=<旧用户id>`, `tenant_id='org_default'`
- 原 `scope='shared'`（任意 tenant_id）→ `user_id=NULL`, `tenant_id='org_default'`

## 二、目标架构（多用户协作 · 一张图）

```
            ┌─────────────────── 组织 org_default（隐式全局唯一）───────────────────┐
            │                                                                      │
   多个用户  │   User A(调度)   User B(船务)   User C(堆场)   ... 并发在线          │
            │      │              │              │                                 │
   认证      │   JWT → contextvars(user_id, org_id) + Principal 全程传播           │
            │      │                                                               │
   资源      │   ┌──────────── 组织共享池 (scope=shared / org 级知识库) ────────┐  │
            │   │  记忆(shared) · 知识库 · 实体图谱 · workflow(预留) · 技能      │  │
            │   └──────────────────────────────────────────────────────────────┘  │
            │   ┌──────────── 个人私有 (按 user_id 隔离) ──────────────────────┐  │
            │   │  记忆(private) · 会话/session · core_memory 个人画像          │  │
            │   └──────────────────────────────────────────────────────────────┘  │
            └──────────────────────────────────────────────────────────────────────┘
                              │
                   Postgres（连接池，支撑并发写）

```

## 三、实施计划

三个 Phase，建议顺序执行。**总量约 16–22 人天**（含知识库 org 化、前端/WS、工作区迁移）。每个 Task 标注改哪个文件、做什么、验收点。

### Phase 1：身份与上下文（多用户的前提）~5 人天

> 让"谁在操作"全程可知，把 tenant_id 的双重语义拆开；认证 SSOT 与前端/WS 一次改齐。

- [x] **T1.1 拆开 org/user 语义（后端常量）**
  - 新增 `tars/org.py`（或 `config/org.py`）：`ORG_ID = "org_default"`。
  - 改 `main.py` 登录审计等：`tenant_id` 不再 = `user.id`。
  - 验收：两用户登录后逻辑 org 均为 `org_default`，user_id 不同。

- [x] **T1.1b（可选，尽早演示共享）** 在 T2 完成前临时强制 Agent/检索传入 `ORG_ID`，便于联调；**不替代** T2 schema 迁移。

- [x] **T1.2 JWT 签发/校验 + 会话表**
  - 复用 `user_store` 的 `password_hash`。
  - 新增 `gateway/jwt_auth.py`：HS256，payload `sub=user_id`, `org_id`, `exp`；可选 refresh。
  - **JWT 持久化**：新增 `auth_tokens` 表（`jti`, `user_id`, `expires_at`, `revoked`）或扩表——**不要**把现有 `user_sessions`（user↔session_id）当 token 表。
  - 登录 `POST /api/auth/login` 返回 `{ access_token, refresh_token?, user }`；保留 `api_key` 字段供集成。
  - `gateway/auth.py` 单 env `TARS_API_KEY` 仅服务机器路径（`/api/invoke` 等）。
  - 验收：错密 401；对密拿 token；无 token 401；过期 token 401。

- [x] **T1.3 contextvars 全局传播**
  - 新增 `tars/context.py`：`current_user_id`, `current_org_id` + getters。
  - `UserContextMiddleware`：JWT 解析后写入，请求结束 reset。
  - 验收：任意 endpoint `get_current_user_id()` 正确，无需手传 Header。

- [x] **T1.4 统一 Principal（`api/_auth.py`）**
  - `resolve_authenticated_principal`：JWT 路径 `org_id=ORG_ID`，`user_id` 来自 token；API Key 路径绑定 user，**禁止**非 admin 用 `X-Tenant-Id` impersonate（单 org 下删除或仅 bootstrap 文档化）。
  - 全路由改为依赖 `require_authenticated_user`（JWT 或 API Key 二选一）。
  - 验收：用户 A 的 Key 不能读到用户 B 的 private 会话（在 T2 完成后做 e2e）。

- [x] **T1.5 前端 + WebSocket 鉴权**
  - `frontend/src/stores/auth.ts`：存 `access_token`，不再默认长期依赖裸 `api_key` 调 API。
  - `frontend/src/api/index.ts`：`Authorization: Bearer` 替代 `X-API-Key`（集成场景可保留 Key 配置页）。
  - `frontend/src/utils/websocket.ts`：`?token=` 或首帧 `auth` 消息，**禁止**仅 `api_key` query（会议 WS 同步）。
  - 验收：浏览器登录 → Chat WS 连上；登出后 WS 拒绝。

### Phase 2：组织池数据模型（多用户共享/私有正确隔离）~5–6 人天

> 补 schema、改过滤、统一向量库与知识库；不是只改 SQL 条件。

- [x] **T2.1 记忆表结构 + 过滤修正**
  - `connection.py`：`ALTER TABLE memories ADD COLUMN user_id TEXT`（PG/SQLite 迁移脚本同步）。
  - 按 §一「数据回填规则」迁移历史行。
  - `memory_repo.py`：查询改为 `tenant_id=ORG_ID AND (scope='shared' OR user_id=?)`，`?` 来自 contextvars；写入 private 带 `user_id`，shared 则 `user_id IS NULL`。
  - `get_memory` / 按 id 读：private 须校验 `user_id` 匹配当前用户。
  - 验收：A private → B 搜不到；A shared → B 搜到；A 两类对自己可见。

- [x] **T2.2 Chroma 记忆向量库组织级（关键）**
  - `vectorstore/chroma_client.py`：collection `{name}_org_default`；private 用 metadata `user_id` / `scope` 过滤。
  - 脚本：合并各 `{name}_{user_id}` → `_org_default`，条数校验 + 备份 `data/vectorstore`。
  - 验收：A 写 shared，B 语义检索可召回。

- [x] **T2.3 实体图谱确认全局共享**
  - 表结构不改。加测试：A 录入 QC-7 实体 → B 提问可召回关联记忆。
  - 验收：通过 `test_*` 或 e2e 断言。

- [x] **T2.4 会话 + core_memory 用户私有**
  - `sessions`：列表/读消息均 `WHERE user_id=? AND tenant_id=ORG_ID`（核对所有入口）。
  - `core_memory`：加 `user_id`，唯一约束改 `(user_id, key)`；迁移默认 user 或按 session 归属回填。
  - 验收：A 会话列表、persona B 不可见；A 改 persona 不影响 B。

- [x] **T2.5 知识库 org 池（必做，原稿遗漏）**
  - `document_collections.tenant_id` 统一 `org_default`；`knowledge/access.py`、`api/knowledge.py`、`insight/knowledge_bridge.py`、会议入库等查询改为 org 级。
  - **删除知识库路由的 `x_tenant_id` Header 依赖**（`api/knowledge.py:118,148` 等 `Header(default="default")` 取 tenant 的入口），改为从 contextvars 取 `ORG_ID`，与 T1.3/T1.4 上下文传播对齐，避免双轨打架。
  - Chroma `knowledge_{coll_id}` 调用处 tenant 参数收口为 `ORG_ID`。
  - 迁移：各用户 tenant 下的 collection 合并或改 tenant_id（幂等脚本 + 文档条数校验）。
  - 验收：A 上传/入库文档，B `search_knowledge` / Insight 检索可命中。

### Phase 3：Postgres 并发底座 ~6–8 人天

> 换引擎 + 迁移 + 并发策略写清（PG ≠ 多 worker 就绪）。

- [x] **T3.1 Postgres 连接层 + 连接池**
  - `connection.py`：按 `DATABASE_URL` 选 sqlite/postgres；Postgres 用 `psycopg`(3) + 连接池。
  - `sql_dialect.py`：FTS5↔`tsvector`/`pg_trgm`、`?`↔`%s`、`INSERT OR REPLACE`↔`ON CONFLICT` 等。
  - 验收：`DATABASE_URL=postgres://...` 启动建表成功，冒烟通过。

- [x] **T3.2 全文检索方言适配**
  - `memory_repo` FTS 走 dialect 分支。
  - 验收：PG 与 SQLite 关键词检索结果等价（抽样用例）。

- [x] **T3.3 数据迁移脚本（含工作区）**
  - `scripts/migrate_sqlite_to_pg.py`：全表导出导入 + T2.1 回填 + T2.5 知识库 tenant 归一。
  - Chroma：复用 T2.2 脚本。
  - **工作区/Evolution**：`~/.tars/agents/{user_id}/` → `~/.tars/workspaces/org_default/`（SOUL/AGENTS 组织级；`USER.md` 按 user 子目录或 DB core_memory）；`ApplyEngine` 与 `WorkspaceManager` 路径对齐，避免进化写回 no-op。
  - 验收：迁移后登录、历史会话/记忆/知识库/人格可见；进化 tuned 段仍生效。

- [x] **T3.4 并发验证 + 部署约定**
  - 压测：N 用户同时写记忆/读知识库，无串数据、无 `database is locked`（PG）。
  - `deploy/docker-compose`：Postgres 服务；日志带 `request_id` + `user_id` + `org_id`（**不**要求完整 metrics，见 §四）。
  - **多 worker 策略（已决策：v5.0 = 方案 A）**：
    - **方案 A（v5.0 锁定）**：`uvicorn --workers 1` + Postgres 连接池；`deploy` 配置写死 `workers=1`；release notes 写「单进程多协程」。理由：LLM IO 密集 + 几十人企业内部规模，单 worker asyncio 已够；规避跨进程唤醒复杂度。
    - **方案 B（推迟 v5.1+）**：需多副本/上百并发时再做 T3.5，方可 `--workers > 1`。
  - 验收：方案 A 下 `workers=1` 压测通过；日志可追踪到 user。

- [ ] **T3.5 跨 worker 会话状态（推迟 v5.1+，本版本不做）**
  - 仅当未来选方案 B（`--workers > 1`）时实施。Approval waiters、Handoff、`FollowUpQueue` cancel 标志（均为进程内 `dict`/`asyncio.Event`）迁入 **Redis 或 PG 表 + NOTIFY** 做跨进程唤醒。
  - 验收：workers=2 时，A 发起 shell 审批，路由到任意 worker 可完成；handoff accept 不丢。

## 五、风险与依赖

1. **Postgres 迁移**：FTS/占位符/JSON 差异。缓解：sql_dialect 收口 + 双库 pytest + SQLite 回退开关（仅 dev）。
2. **Chroma 合并（T2.2）**：做错丢向量。缓解：备份 + 幂等 + 条数对账。
3. **memories 缺 user_id（T2.1）**：若只改 WHERE 不重填，会全员可见或全员不可见。缓解：迁移脚本 + 单测矩阵 A/B/private/shared。
4. **知识库 tenant 分岛（T2.5）**：只改记忆不改 KB，验收第 5 条失败。
5. **core_memory 全局 UNIQUE（T2.4）**：多人串 persona，必改表。
6. **多 worker 内存状态**：未做 T3.5 却开 `--workers 2` → 审批/handoff 随机失败。缓解：方案 A 写死 workers=1 或 CI 断言。
7. **repository 层**：已存在 `database/repositories/*`，T3 工作量可信。
8. **前端/WS 与后端不同步（T1.5）**：会导致「API 已 JWT、浏览器仍 Key」半残状态，须同 PR 或同里程碑合并。

## 六、验收总标准（v5.0.0 达成定义）

1. 两个以上用户各自账号密码登录（**JWT**），同时在线，private 数据互不串。
2. A 写入 **shared 记忆/港航实体**，B 的 Agent 能召回；A 的 **private 会话/记忆** B 看不到。
3. 后端跑在 **Postgres** 上，并发写无 `database is locked`、无用户级数据错乱。
4. 历史 **SQLite + Chroma + 工作区** 迁移完整，用户无感。
5. **知识库 org 池**：A 入库文档，B 检索/问答可命中（T2.5）。
6. **并发部署（方案 A）**：`deploy` 与 release notes 明确 `uvicorn --workers 1`；压测报告存档；不得宣称「多 worker 生产就绪」除非 v5.1+ 完成 T3.5。
