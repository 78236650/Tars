## 组 A — 测试未带认证 headers（~16，机械批量，改测试）

**症状**：`assert 401 == 200`（或 `== 403`），返回体常为 `{"detail":"Invalid API key"}`。
**根因**：v5 给这些 endpoint 加了 `Depends(require_authenticated_user)` / `require_module(...)` / `require_admin`，但测试用 `TestClient` 请求时没带认证头。与已修的 Fix 8 完全同型。
**标准改法**：用 conftest 既有 helper 注入认证头：
- 普通用户：`from tests.conftest import setup_knowledge_auth`（返回 `({"X-API-Key": ...}, user)`），请求加 `headers=auth_headers`。
- 需 admin 的端点：用能创建 admin 角色的 helper（查 conftest 是否有 `setup_admin_auth`；否则 `UserStore.create_user(role=UserRole.ADMIN)` 后 `init_auth`）。
- 数据作用域：v5 下 principal 的 `tenant_id` 恒为 `ORG_ID`（`tars.org.ORG_ID = "org_default"`）。测试预置数据的 `tenant_id` 必须用 `ORG_ID`，不能再用 `"default"`（同 Fix 8 的 404 修法）。

**清单**（文件::用例 → 期望码）：
- `test_admin_memory_api.py`：`test_admin_users_response_shape`(401→200)、`test_admin_user_memories_response_shape`(401→200)、`test_admin_endpoints_require_admin_role`(401→403，需用**非 admin** 已认证用户验证 403)
- `test_audit.py::TestAuditApi`：`test_admin_can_list_all_tenants`(401→200)、`test_non_admin_forbidden`(401→403)、`test_filter_by_tenant_id`(401→200)
- `test_default_skills.py::TestSkillAPIIntegration`：`test_list_default_skills`(401→200)、`test_disable_then_enable`(401→200)
- `test_tools_skills.py::TestSkillsAPI::test_list_skills_empty`(401→200)
- `test_knowledge_m3_m4.py::test_reindex_estimate_api`(401→200)
- `test_kb_promotion.py::test_save_does_not_publish_by_default`(401→200)
- `test_wiki_smoke_e2e.py::test_upload_routes_small_md_to_wiki`(401→200)
- `test_vector_upgrade.py`：`test_batch_upload_two_files`(401→200)、`test_batch_upload_partial_failure`(401→200)
- `test_meeting_asr_settings_api.py`：`test_get_asr_settings_includes_whisper_options`、`test_set_asr_whisper_model`、`test_set_asr_whisper_model_rejects_invalid`（均 `Invalid API key`）

**验证**：逐文件 `pytest tests/<file> -q`。

## 组 B — `create_user` 鉴权早于输入校验（2，需设计决策）

**症状**：`test_auth_login_api.py::test_create_user_requires_password`(401≠422)、`test_create_user_rejects_short_password`(401≠400)。
**根因**：`tars/main.py:729` `POST /api/users` 加了 `principal=Depends(require_authenticated_user)`。FastAPI 依赖先于请求体 Pydantic 校验执行，故缺/弱密码请求在校验前就被鉴权拦成 401，测试拿不到预期的 422/400。
**决策点（须确认，勿擅改）**：
- 若 create_user **应当**需认证：测试改为带认证头后再断言 422/400（改测试）。
- 若 create_user 是**首个用户引导/公开注册**入口：移除该依赖或改可选认证（改生产）。
  → 结合 v5 多用户设计意图（`docs/.../tars-v5.0.0-multiuser-design.md`）与 admin 引导流程判断。
**验证**：`pytest tests/test_auth_login_api.py -q`。

## 组 C — memory_tree API 作用域 + 缺 `_resolve_tree_tenant`（9，生产+测试，部分需决策）

**症状**（`test_memory_tree_api.py`）：
- `test_groups_by_primary_entity`(0==2)、`test_orphan_bucket`(0==1)、`test_bucket_truncation` — 关系/实体没建出。
- `test_get_tree`/`test_provenance_view`/`test_tree_search`(403≠200)、`test_tree_admin_user_id_forbidden_for_non_admin`(403) — 作用域/admin-view 鉴权。
- `test_tree_graph` — `sqlite3.IntegrityError: NOT NULL constraint failed: relations.tenant_id`。
- `test_tree_relations`(StopIteration)。
- line 172/179 — `ImportError: cannot import name '_resolve_tree_tenant' from tars.api.memory`。

**根因**：
1. `relations.tenant_id NOT NULL`（Fix 2 建表设了 NOT NULL，正确）——写入方传了 `None`。查 `tree_builder`/`reflector` 写入时 `tenant_id` 来源（v5 应为 `ORG_ID`，确认实例化是否传入）。这是 0==2 / StopIteration 的连锁源。
2. `_resolve_tree_tenant` 测试期望存在、生产 `memory.py` 没有；memory.py 已用 `ORG_ID` + `_apply_admin_view_user`(line 110) 做作用域，疑似被重命名/内联。
   **决策点**：补 thin helper `_resolve_tree_tenant(principal, user_id)`（返回 `ORG_ID` 并复用 `_apply_admin_view_user` 的 admin-view 校验）；或改测试调现有函数。
3. 403：tree 端点 admin-view（`?user_id=`）对非 admin 应 403、对自身应 200。核对 `_apply_admin_view_user`(line 112-113) 与测试期望，并确保测试带**自身**已认证用户。

**验证**：`pytest tests/test_memory_tree_api.py -q`。先解 C-1（tenant_id 写入），很可能连带修掉数个非鉴权失败。

## 组 D — schema 漏建表/漏列（~14，改生产，优先做）

**症状**：
- `sqlite3.OperationalError: no such table: skills_v3`
- `no such table: tasks`（3 处，`test_database_facade_characterization.py` 等）
- insight：`no such column: version`（9 处，`test_insight_profile_pipeline.py` 全 ERROR）

**根因**：表/列的 DDL 存在于 `connection.py`/`connection_pg.py` 或某模块，但**未在 `Database()` 主初始化路径无条件建出**（同 Fix 2「relations」、Fix 9「bi_datasources」型）。`test_insight_profile_pipeline` 用 fixture 自建库，未走 INS 迁移，故缺 `version` 列。

**改法**：
1. `skills_v3` / `tasks`：确认其 `CREATE TABLE` 是否在 `init_schema()` 内被调用；若挂在某个延迟/条件路径，移入主 schema（参照 Fix 9 把 `run_insight_ins2_migrations` 接进 SQLite 路径的做法）。
2. insight `version` 列：定位 insight profile 表 DDL（疑 `insight_profile_runs`/`profile_snapshots`），确认 `version` 列是否在最新迁移里；`test_insight_profile_pipeline` 的 fixture 需调用 INS 迁移函数建全 schema。检查 `migrate_sqlite_to_pg.py` 是否带上这些表。

**验证**：`pytest tests/test_insight_profile_pipeline.py tests/test_database_facade_characterization.py -q`。
> 注：D 修完后 **先重跑全量**——schema 是多组的连锁根因，可能顺带解开 C/E 的部分失败。

## 组 E — insight tenant 冲突 / 数据源缺失（~9，夹具为主，部分需查生产）

**症状**：
- `belongs to tenant "..." refusing to rewrite`（`job_runner.py:229`）—— Chroma collection 的 tenant 与请求 tenant 不一致。
- `{"detail":"数据源不存在"}`（`suite_runner.py:239/286/339`）、`{"detail":"metric not found"}`(272)、`smoke ...:147` 404。

**根因**：v5 作用域统一到 `ORG_ID` 后，insight 测试夹具创建数据源/collection 用的 tenant 与运行时 `org_scope(principal)` 不一致（同 Fix 8 的 404 型，发生在 insight 域）。`belongs to tenant` 那条还叠加了 Chroma collection 复用时的 tenant 校验。

**改法**：
- 夹具创建 datasource/collection 时 tenant 统一用 `ORG_ID`；suite_runner 的请求带正确认证（principal.tenant=ORG_ID）。
- `belongs to tenant`：确认 `job_runner` 写 Chroma 时的 tenant 取值与建 collection 时一致（都应 `ORG_ID`）。若该用例还依赖 Ollama（见组 G 的 502），则属环境依赖，单独标注。

**验证**：`pytest tests/insight/ -q`（注意区分 G 类环境失败）。
