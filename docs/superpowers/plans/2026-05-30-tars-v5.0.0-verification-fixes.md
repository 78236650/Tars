## Fix 1 🔴 chunker 无限循环（阻断 CI）

**定位证据**（faulthandler 在 25s 超时转储的栈顶）：
```
File "tars/knowledge/chunker.py", line 65 in _fixed_length_chunk
File "tars/knowledge/chunker.py", line 31 in chunk
File "tests/test_vector_search_knowledge_base.py", line 41 in test_chunk_metadata
```

**根因**：`test_chunk_metadata` 用 `DocumentChunker(chunk_size=50, strategy="fixed")`，`chunk_overlap` 取默认值 `50`。
`chunker.py:65` 的步进 `start += self.chunk_size - self.chunk_overlap` = `50 - 50 = 0`，`start` 永不前进。
`line 66` 的 `if start >= end: break` 是无效防护——`start=0`、`end=11`（"hello world"），`0 >= 11` 永远为假。

**影响**：任何 `chunk_size <= chunk_overlap` 的调用都会死锁主线程；这是导致整个 pytest 套件挂死、并连带触发 Fix 3 NameError 的总根源。

**修复**（`tars/knowledge/chunker.py:55-69`）：步进至少为 1。
```python
    def _fixed_length_chunk(self, text: str) -> List[str]:
        """固定长度分块，带重叠"""
        chunks = []
        start = 0
        text_len = len(text)
        step = max(1, self.chunk_size - self.chunk_overlap)  # FIX: 防止 overlap>=size 时步进<=0 死循环

        while start < text_len:
            end = min(start + self.chunk_size, text_len)
            chunks.append(text[start:end].strip())
            if end >= text_len:
                break
            start += step

        return [c for c in chunks if c]
```

**离线验证**：死亡 case `("hello world", size=50, overlap=50)` → 返回 `['hello world']`（单块）；正常 case `("a"*120, size=50, overlap=10)` → 3 块，不变。

## Fix 2 🔴 缺失 `relations` 表（运行时 + 4 测试崩溃）

**定位证据**：
```
tests/test_relations_tenant_isolation.py FFFF
E   sqlite3.OperationalError: no such table: relations
```

**根因**：存在两张**不同**的表，被混淆：
- `memory_relations`（DDL 已建，`connection.py:521` / `connection_pg.py:514`）：列 `id, source_id, target_id, relation_type, weight, created_at`。**全代码库无任何读写**，仅 `domain_schema.py:27` 一句注释提及——孤儿表。
- `relations`（DDL **从未创建**）：列 `tenant_id, from_entity, to_entity, predicate, confidence, created_at`。被生产代码实际读写：
  - 写：`tars/memory/reflector.py:332` `INSERT OR REPLACE INTO relations(...)`
  - 读：`tars/memory/tree_builder.py:295 / 549 / 650` `FROM relations`
  - 测试：`tests/test_relations_tenant_isolation.py`

**重要**：这是**早已潜伏**的 bug，非 v5 引入——`git show HEAD:...connection.py` 同样只有 `memory_relations`。但只要运行时走到关系抽取（reflector）或实体树构建（tree_builder），就会 `no such table: relations` 崩溃。v5 的 PG 路径同样受影响。

**修复**：在 SQLite 与 Postgres 两处 DDL 各补建 `relations` 表（列与主键须匹配 `INSERT OR REPLACE` 语义）。

`tars/database/connection.py`（紧随 `memory_relations` 之后）：
```python
        cursor.execute("""
            CREATE TABLE IF NOT EXISTS relations (
                tenant_id   TEXT NOT NULL,
                from_entity TEXT NOT NULL,
                to_entity   TEXT NOT NULL,
                predicate   TEXT NOT NULL,
                confidence  REAL DEFAULT 0.7,
                created_at  TEXT NOT NULL,
                PRIMARY KEY (tenant_id, from_entity, to_entity, predicate)
            )
        """)
```

`tars/database/connection_pg.py`（同一位置，用其 `_exec` 包装；PG 等价语法）：
```python
    _exec(
        cursor,
        """
        CREATE TABLE IF NOT EXISTS relations (
            tenant_id   TEXT NOT NULL,
            from_entity TEXT NOT NULL,
            to_entity   TEXT NOT NULL,
            predicate   TEXT NOT NULL,
            confidence  DOUBLE PRECISION DEFAULT 0.7,
            created_at  TEXT NOT NULL,
            PRIMARY KEY (tenant_id, from_entity, to_entity, predicate)
        )
        """,
    )
```

> 注：主键 `(tenant_id, from_entity, to_entity, predicate)` 是 `INSERT OR REPLACE`（reflector）去重语义所必需。PG 迁移脚本 `migrate_sqlite_to_pg.py` 若按表枚举迁移，确认其会带上 `relations`。
> 可选清理：若确认 `memory_relations` 无人使用，后续可单独删除该孤儿表（**不在本 fix 范围**，避免扩大改动）。

## Fix 3 🟡 `NameError: require_authenticated_user`（连带，无需独立修复）

**现象**：首次全量 `pytest -q` 在收集阶段报 `tars/main.py:710 NameError: name 'require_authenticated_user' is not defined`（崩 `test_app_boots.py` / `test_evolution_metrics_api.py`）。

**判定：非独立 bug。** 证据：
1. `from tars.main import app`、`from tars.api._auth import require_authenticated_user`、`from tars.context import ...` 单独导入全部成功。
2. 两个被崩文件单独/成对收集，重复 3 次全部通过。
3. 修掉 Fix 1 思路后，全量 `pytest --co`（仅收集、不触发死循环）：**1183/1190 collected，0 error，exit 0**，NameError 不复现。

**结论**：根因是 Fix 1 的死循环——全量运行挂死后进程被中断，`sys.modules` 残留 `tars.main` 半初始化状态，导致后续偶发收集报错。**修复 Fix 1 后此现象消失，无需单独改动。**
