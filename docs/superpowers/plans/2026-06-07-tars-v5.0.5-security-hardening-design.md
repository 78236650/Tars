# TARS v5.0.5 设计文档：安全加固与企业级就绪

> 主题：基于 v5.0.4 企业级审计的安全修复与生产就绪改造
> 日期：2026-06-07
> 状态：设计稿（文档优先，代码未动）
> 关联：[开发步骤](../../03-实施计划/v5.0.5-development-steps.md) · [执行计划](../../03-实施计划/v5.0.5-execution-plan.md)

## 1. 背景

v5.0.4 收尾后，对全平台做了一次多 Agent 对抗式审计（49 个 agent，四轴：安全 / Agent 基础能力 / 模块健全 / 企业级就绪）。共产出 44 条发现，经独立对抗验证后 **39 条坐实、5 条证伪**，分级为 3 个 critical、25 个 high、11 个 medium。

本设计文档把 39 条确认问题整理为可落地的修复方案，归入 v5.0.5。核心判断：

- TARS 的**架构骨架是企业级的**（JWT+APIKey 双认证、RBAC 角色模板、工具权限闸、审批 human-in-the-loop、审计日志、租户工作区隔离、模块开关、SQLite/PG 双轨）。
- 但**尚不满足"可生产部署的企业级 Agent OS"**，卡在三类硬伤：① 存在认证裸奔端点与工具沙箱绕过等安全缺口；② 缺结构化日志/metrics/trace 等可观测性；③ 缺备份迁移、优雅关闭等运维基建。

## 2. 设计目标与非目标

### 目标
1. **闭合所有 critical/high 安全缺口**，使平台可通过基础安全审计。
2. **补齐生产就绪硬指标**：结构化日志、限流接线、请求体限制、优雅关闭、备份迁移。
3. **强化 Agent 基础能力的可靠性**：工具循环超时/降级、审批持久化、记忆降级、全链路 trace。
4. 全程**最小改动、可验证、可回滚**，不引入新架构范式。

### 非目标（本版本明确不做）
- **不做多租户 SaaS 改造**。tenant_id 恒为 ORG_ID 是 v5.0 的有意设计（单组织多用户），重建隔离层超出本版范围。
- **不做横向扩展（多 worker/多机）**。单进程单 worker 是当前有意约束；本版仅加防护栏，不改架构。
- **不引入重型外部依赖**（Redis/Celery/K8s）作为强制项；涉及处给出可选方案，默认保持单进程可用。

## 3. 现状评估矩阵

| 维度 | 评级 | 结论 |
|------|------|------|
| 多用户基础 | ✅ 满足 | 单组织多用户 + user_id 私有隔离，认证中枢设计正确 |
| 多租户 SaaS | ❌ 不支持 | tenant_id 恒为 ORG_ID（有意设计，非缺陷） |
| 安全性 | ⚠️ 有致命缺口 | 认证中枢稳，但有裸奔端点 + 沙箱可绕过 |
| Agent 基础能力 | ⚠️ 部分 | 骨架完整，缺超时/降级/取消/可观测 |
| 生产就绪度 | ❌ 不达标 | 缺结构化日志/metrics/trace、备份迁移、优雅关闭 |

## 4. 修复方案分批

修复按风险与依赖分三批。批次一是上线硬阻塞，必须先做；批次二补生产就绪；批次三增强 Agent 可靠性。

### 批次一：安全硬阻塞（critical + 安全 high）

#### S1. skills.py 端点认证缺失【critical】
- **问题**：`api/skills.py` 13 个端点中仅 3 个挂了认证（`list_skills`、`get_skill`、`/{skill_id}`），其余 **10 个裸奔**：`/stats`、`/pending-archive`、`/{skill_id}/stats`、`/{skill_id}/archive`、`/{skill_id}/activate`、`/create-prompt`、DELETE `/{skill_id}`、`/reload`、`/{skill_id}/enable`、`/{skill_id}/disable`。未授权者可删技能、重载技能库、增删改技能状态。
- **方案**：采用 `bi.py` 已验证的全局依赖模式，一行覆盖整个 router：
  ```python
  router.dependencies = [Depends(require_module("skills"))]
  ```
  系统级操作（`reload`、DELETE）再单独叠加 `require_admin`。
- **取舍**：全局依赖优于逐端点添加——后者易遗漏，且与 bi.py 风格一致。
- **验证**：未带 token 请求各端点应返回 401/403；带普通用户 token 请求 `reload` 应 403。

#### S2. knowledge 模块删除后残留引用【critical】
- **问题**：`tars/knowledge/` 目录已删，但 **20+ 处 lazy import 仍存活**：整个 `api/knowledge.py`（18 处）、`api/meeting.py:832`、`agent/prompt_builder.py:208`、`memory/turn_knowledge_publisher.py`。lazy import 使启动不崩，但触达即 `ModuleNotFoundError`。
- **方案**：
  1. 删除 `api/knowledge.py` 整个路由（及 main.py 的挂载），或保留为 410 Gone stub。
  2. 清理 `api/meeting.py:832` 的 `ensure_knowledge_schema` import——meeting 转存改用 WikiStore（同文件 894 行已有 import）。
  3. 清理 `agent/prompt_builder.py:208` 的 `search_knowledge` 调用——走 wiki 检索或直接跳过。
  4. 清理 `memory/turn_knowledge_publisher.py` 的条件 import——此处与 v5.0.4 双向链接升级相关，已部分用 wiki，去掉 knowledge 兜底分支。
  5. 加预部署校验：启动时显式 import 所有 API 模块，CI 中跑一次 import smoke test。
- **取舍**：彻底删除优于补 stub——死代码留着只会再次踩坑；但 meeting/memory 的转存功能需用 wiki 等价替换，不能直接删。

#### S3. 工具沙箱可被绝对路径绕过【high】
- **问题**：`shell`、`python_exec` 工具不强制 `_allowed_dirs`，`cat /etc/passwd`、`open('/etc/passwd')` 直接成功。WorkspaceSandbox 只拦相对路径遍历。单组织内是"用户间越界"，多租户则是数据泄露。
- **方案**：
  1. shell 工具加 `_validate_command_path_safety()`，拦截命令中访问 workspace 外绝对路径的模式。
  2. python_exec 加受限执行环境（覆写 `open`，校验绝对路径在 allowed_dirs 内）。
  3. dispatcher 对高危工具（shell/python_exec/file_write）**fail-closed**：拿不到 workspace 时拒绝执行。
- **取舍**：python_exec 完全沙箱化代价高，本版先做 `open` 拦截 + 危险 import 告警，完整沙箱（cgroup/容器）列入后续。

#### S4. 认证失败不进审计日志【high，合规阻塞】
- **问题**：`_auth.py` 中无效 JWT、越权、admin 校验失败全部直接 raise HTTPException，**完全不写审计日志**。SOC2/ISO27001 要求记录失败访问尝试。
- **方案**：在 `_auth.py` 各 40x 抛出前调用 `audit_logger.log_permission_denied()` / `log_login(success=False)`；`require_module` 失败同样记录。
- **取舍**：审计写入须 fail-safe（`safe_audit()` 包裹），不能因审计失败阻断认证主流程。

#### S5. 密钥硬编码【high】
- **问题**：`main.py` 硬编码 `DEFAULT_ADMIN_PASSWORD='Admin123!'`；JWT secret 有 dev fallback。
- **方案**：移除硬编码默认密码，改为环境变量必填或首次启动 API 初始化；生产缺 `TARS_JWT_SECRET` 时 fail-fast（已部分实现，补全）；Dockerfile 支持 Docker secrets 挂载。
- **取舍**：API key 数据库加密列入批次二（涉及 schema 迁移）。

#### S6. REST 限流形同虚设 + 无请求体上限【high，DoS】
- **问题**：`gateway/rate_limit.py` 定义了限流但**没接到任何路由**；memory/audit 等端点无请求体大小限制，可 DoS。
- **方案**：
  1. 把 `RateLimiter` 接入 API 路由（至少 `invoke.py` 等高频写入端点）。
  2. audit.py 查询参数加 `max_length`；memory.py 的 Pydantic 模型加 `max_length`（core block 10K、memory 100K、import 5MB）。
  3. 全局 RequestValidationError 处理器返回 422 而非 Uvicorn 的 502。
- **取舍**：分布式限流（Redis）列入可选项；本版用内存限流满足单进程部署。

### 批次二：生产就绪（生产 high）

#### P1. 可观测性：结构化日志【high，生产阻塞】
- **问题**：129 处 `print()` vs 19 处 logging，无统一格式、无级别控制、无聚合。生产出问题无法定位。
- **方案**：
  1. 新建 `tars/logging/` 统一日志配置模块（dictConfig + 标准 Formatter，含 timestamp/level/logger/module）。
  2. main.py 启动期初始化日志。
  3. 关键模块（agent/tools/api/memory/search）的 `print()` 替换为 logger（分 info/warning/error）。
  4. 可选：结构化 JSON 日志（python-json-logger）以对接 ELK。
- **取舍**：本版先做框架 + 核心路径迁移；129 处不必一次全改，按模块优先级推进。

#### P2. 全链路 trace_id【high】
- **问题**：无贯穿请求的 trace_id，跨模块调用（agent→tool→dispatcher→LLM）无法追踪，日志无法关联同一请求。
- **方案**：
  1. `tenant/context.py` 加 `trace_id` ContextVar。
  2. 新建 `TraceIDMiddleware`（在 UserContextMiddleware 之前）生成/传播 `X-Trace-ID`。
  3. 日志 Formatter、审计日志、dispatcher context 注入 trace_id。
  4. 异步任务边界透传 trace_id。
- **取舍**：不引入 OpenTelemetry/Jaeger（重依赖）；用 ContextVar + 日志注入实现端到端追踪即可满足合规。

#### P3. metrics 导出【high】
- **问题**：无 Prometheus/StatsD，无延迟分布、token 聚合、连接池状态。
- **方案**：集成 `prometheus-client`，FastAPI 中间件埋 HTTP 请求计数+延迟直方图，dispatcher 埋工具执行耗时，provider_usage 加聚合查询，暴露 `/metrics`。
- **取舍**：Grafana 仪表板与告警规则作为运维侧配置，不入代码库；本版只保证 metrics 可导出。

#### P4. 数据库备份与迁移版本管理【high，合规阻塞】
- **问题**：无自动备份；schema 迁移靠 `ALTER TABLE ... except pass`，无版本、无回滚。
- **方案**：
  1. 新建 `schema_versions` 表 + `database/migrations/` 版本化迁移文件 + `apply_migrations()`。
  2. 备份 API 端点（admin）+ systemd timer 日备份（SQLite 原子拷贝 / PG pg_dump）。
  3. 灾难恢复 runbook 文档（RTO/RPO）。
- **取舍**：不强制引入 Alembic；用轻量自建版本表，保持单进程零新依赖。

#### P5. 优雅关闭【high】
- **问题**：shutdown 仅关 scheduler/ASR pool，不等在途请求、不优雅断 WebSocket、无 SIGTERM 处理。容器滚动更新丢任务。
- **方案**：lifespan 加全局任务超时等待；ConnectionManager 加 `disconnect_all(timeout)`；main.py 加 SIGTERM/SIGINT handler；uvicorn 显式 `timeout_keep_alive`。

#### P6. API key 数据库加密 + 错误响应统一【high/medium】
- **方案**：user.api_key 列加密存储；定义统一 `ApiResponse`/`ApiErrorResponse` 模型 + 全局 HTTPException 处理器，错误码体系化。
- **取舍**：统一响应格式是 breaking change，需同步前端；本版先加全局错误处理器（向后兼容），响应包装分阶段迁移。

### 批次三：Agent 能力增强（agent-capability high）

#### A1. 工具循环超时与上下文控制
- 工具结果长度上限 + 超阈值截断；`max_rounds` 从 None 改为可配默认值（10）；接近 token 上限时压缩早期消息。
- dispatcher 层为单个工具加 `asyncio.wait_for` 兜底超时（防御纵深）；ToolResult 加 `recoverable`/`retry_suggested` 结构化字段。
- prompt fallback 模式 JSON 解析改多趟 + 校验 + 解析失败追问重试（本地模型失败率从 10-20% 降到 <2%）。

#### A2. 审批闸可靠性
- timeout 与 denied 对 agent 返回不同信号（agent 可区分重试 vs 放弃）。
- 审批状态持久化（不再纯内存），进程重启可恢复。
- 超时前提醒 + 超时后宽限窗口内的迟到审批可恢复。

#### A3. 记忆系统降级
- Reflector 三层降级：LLM → HeuristicTurnExtractor → 最小归档（log_episode）。LLM 宕机时记忆仍增长。
- HybridSearch 向量编码失败回退确定性 embedding；FTS 基础分从恒定 0.5 改动态评分；暴露 fallback_depth。

#### A4. Agent 取消与后台任务生命周期
- Agent 维护 `session_id -> [Task]` 追踪；`_abort_if_cancelled` 取消该会话所有后台任务；finally 清理。防连接池耗尽。

#### A5. 并发编排防护
- 子 agent 并发写同一 workspace 加 per-task 锁；编排前做循环依赖（DAG）检测；OrchestrationMemory 多步操作事务包裹。

#### A6. Agent 决策可追溯
- 新建 `agent_decisions` 表，记录技能路由/记忆检索/升格决策（含 trace_id），提供查询端点。支持事后审计与行为可解释。

#### A7. 其他 medium（择机）
- execution_policy 配置热更新（reload 端点）；rate limiter pool 隔离 + 优先级；dead_letters 处理器（重试+告警+重放）；cron 任务超时保护；缓存多 worker 一致性（仅文档说明单 worker 约束）。

## 5. 被证伪的发现（不修，留档备查）

对抗验证否掉 5 条，记录以免重复踩坑：
1. **files.py 堆栈泄露到响应** — 实际只到 stderr，响应仅通用 message。
2. **roles.py 目录遍历** — role_id 只进参数化 SQL，不碰文件系统，定性错误。
3. **无 Dockerfile/K8s/CI** — Dockerfile、docker-compose、CI 均齐全（仅缺 K8s manifest）。
4. **多 worker 全局状态不安全** — 单 worker 是有意设计，非缺陷。
5. **schema 并发变更风险** — 单启动窗口 + WAL + IF NOT EXISTS 已正确处理。

## 6. 风险与回滚

| 改动 | 风险 | 回滚 |
|------|------|------|
| S1 skills 认证 | 前端若调这些端点未带 token 会 401 | 配置层临时放宽，但不建议 |
| S2 删 knowledge 引用 | meeting/memory 转存功能依赖 | 保留 wiki 等价路径，灰度验证 |
| P1 日志迁移 | 大面积改动 | 按模块分批，每批独立可回滚 |
| P4 schema 迁移 | 迁移脚本出错损数据 | 迁移前自动备份 + dry-run |
| P6 统一响应 | breaking change | 全局处理器向后兼容，包装分阶段 |

每批次独立成 PR，独立验证、独立可回滚。批次一为安全硬阻塞，最先合入。
