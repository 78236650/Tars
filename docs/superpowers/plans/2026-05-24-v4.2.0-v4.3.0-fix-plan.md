## 🔴 P1：合并/发布前必修

### F-01 Evolution 写回目录与 Agent 读取目录不一致 — 进化闭环在生产环境是 no-op

- **现象**：optimize 后日志显示 `personality_optimized=True / prompts_tuned=True / subagent_optimized=True`，但下一回合 Agent 不会使用新人格、新 prompt、新子代理配置。
- **根因**：
  1. `ApplyEngine.__init__` 默认 `workspace_base="~/.tars/workspaces"`，写到 `~/.tars/workspaces/{tenant}/SOUL.md`
     位置：[backend/tars/evolution/apply_engine.py:53](../../backend/tars/evolution/apply_engine.py#L53)
  2. Agent 在 `_build_static_prompt` 通过 `WorkspaceManager` 读 `~/.tars/agents/default/SOUL.md`
     位置：[backend/tars/workspace/manager.py:18](../../backend/tars/workspace/manager.py#L18)
  3. `apply_prompt` 写入 `workspace/{tenant}/prompts/{type}.md`，但 `_build_static_prompt` 只读 SOUL+USER+MEMORY，**无 prompts overlay 加载逻辑**
     位置：[backend/tars/evolution/apply_engine.py:112](../../backend/tars/evolution/apply_engine.py#L112)，[backend/tars/agent/agent.py:855](../../backend/tars/agent/agent.py#L855)
  4. `apply_subagent_config` 写入 `workspace/{tenant}/subagents.json`，**SubAgentManager 全局没有 `subagents.json` 引用**
- **处理方式**：
  1. 统一目录：把 `ApplyEngine.workspace_base` 默认值改为 `~/.tars/agents`；构建 SOUL/prompts/subagents 路径时使用 `{workspace_base}/{tenant_id}` 与 `WorkspaceManager` 对齐。
  2. 增加 prompts overlay：`WorkspaceManager.build_context()` 或 `_build_static_prompt` 读取 `workspace/prompts/*.md`，按优先级追加到 system prompt 末尾。
  3. SubAgentManager 启动 + 每次 delegate 前读取 `subagents.json`（可选 lru_cache + mtime invalidation），合并到内置权重。
  4. 现网若已有写到 `~/.tars/workspaces/` 的旧文件，加一次性迁移脚本或在 ApplyEngine 启动时打 warn。
- **涉及文件**：`apply_engine.py`、`workspace/manager.py`、`agent/agent.py`、`agent/subagent_manager.py`
- **验证**：
  - 新增端到端测试：seed events → optimize → 重启 Agent 实例 → assert `_build_static_prompt()` 内容包含新人格段 + tuned prompt 片段。
  - `subagents.json` 写入后调 `SubAgentManager.delegate_task("...")`，断言权重已变化。

### F-02 ToolDispatcher 审批 fail-open — 高危工具安全短板

- **现象**：当 ApprovalService 未初始化、yaml 解析失败或 DB 故障时，shell / python_exec / file_write 等高危工具被**直接放行**。
- **根因**：审批分支被 `except Exception: pass` 包裹。
  位置：[backend/tars/tools/dispatcher.py:122-139](../../backend/tars/tools/dispatcher.py#L122-L139)
- **处理方式**：
  1. 改 fail-closed：任何 exception → return `ToolResult(success=False, error="审批服务不可用，已拒绝执行")`。
  2. 区分两类异常：a) `approval_service is None` → 拒绝；b) `request_approval` 内部异常 → 拒绝并 audit。
  3. 把 try 块内 import 提到模块顶层，import 失败暴露而不是吞掉。
- **涉及文件**：`backend/tars/tools/dispatcher.py`
- **验证**：补 `test_tool_approval.py::test_dispatcher_denies_when_approval_service_missing` / `test_dispatcher_denies_on_yaml_error`。

### F-03 同租户用户可互相审批 — 越权风险

- **现象**：default 部署中 `tenant_id="default"`，**任意已登录用户都能批准他人的 shell 调用**。
- **根因**：授权条件错用 `AND`：
  位置：[backend/tars/api/approvals.py:34-38](../../backend/tars/api/approvals.py#L34-L38)
  ```python
  if request.user_id != principal.user_id and request.tenant_id != principal.tenant_id:
      raise HTTPException(403, ...)
  ```
  当请求方与 principal 在同租户、不同用户时，左条件 True、右条件 False → 整体 False → 放行。
- **处理方式**：
  1. 把策略明确为「仅请求方本人 或 admin」。改为：
     ```python
     if principal.is_admin: return
     if request.user_id != principal.user_id:
         raise HTTPException(403, "无权审批该请求")
     ```
  2. `execution_policy.yaml` 的 `auto_allow_for_roles` 仍生效（在 ApprovalService 内部）。
  3. 若需要"管理员可批 tenant 内所有审批"，单独加 `auto_allow_for_roles: [admin, tenant_admin]` 而非放在 API 鉴权层。
- **涉及文件**：`backend/tars/api/approvals.py`
- **验证**：补 `test_tool_approval.py::test_other_user_cannot_approve`、`test_admin_can_approve_any`。

### F-04 KnowledgeBridge 500ms 超时**完全未生效** + yaml 配置未加载

- **现象**：
  1. 慢的 retriever 会直接阻塞 `MetricQaEngine.ask()`，没有 500ms 截断。
  2. 运维改 `backend/config/insight.yaml` 的 `knowledge_bridge.*` 字段不生效。
- **根因**：
  1. `retrieve_for_question` 是同步方法，无 `asyncio.wait_for`；外层调用也无 `await`。
     位置：[backend/tars/insight/knowledge_bridge.py:39-107](../../backend/tars/insight/knowledge_bridge.py#L39-L107)、[backend/tars/insight/metric_qa_engine.py:476](../../backend/tars/insight/metric_qa_engine.py#L476)
  2. `load_insight_config` 不解析 `knowledge_bridge` 段，`InsightConfig` 也无对应字段；`api/router.py:55` 构造 KnowledgeBridge 时不传 `settings`。
     位置：[backend/tars/insight/config.py:103-175](../../backend/tars/insight/config.py#L103-L175)、[backend/config/insight.yaml:44-49](../../backend/config/insight.yaml#L44-L49)
- **处理方式**：
  1. `retrieve_for_question` 改为 `async def`，内部用 `asyncio.to_thread` 包裹同步检索；外层 `await asyncio.wait_for(..., timeout=settings.timeout_ms/1000)`，`TimeoutError` 捕获后返回 `[]` + `logger.warning("knowledge bridge timeout")`。
  2. `MetricQaEngine.ask()` 路径改为 `await self._knowledge_bridge.retrieve_for_question(...)`。
  3. `InsightConfig` 增 `knowledge_bridge: KnowledgeBridgeSettings`，`load_insight_config` 读取 yaml `knowledge_bridge` 段；`api/router.py` 构造 KnowledgeBridge 时传入 `config.knowledge_bridge`。
- **涉及文件**：`knowledge_bridge.py`、`metric_qa_engine.py`、`insight/config.py`、`insight/api/router.py`
- **验证**：
  - 单测：mock retriever sleep 1s，断言 ≤600ms 返回 `[]`。
  - 单测：yaml `timeout_ms: 200` 写入 → 重新 load_insight_config → bridge.settings.timeout_ms == 200。

## 🟠 P2：Important（应在版本 release 前修）

### F-06 [Phase 2] EvalRunner gate 只对 personality 有效 — eval 门槛形同虚设

- **现象**：B2「优化前后综合分提升 ≥10%」无法可信度量；prompt/skill/subagent 三类写回不会被 eval 退步保护。
- **根因**：
  1. `orchestrator.py:56,128` 在 before/after context 只填 `{"personality": ...}`，未传 prompts/skill/subagent 信息。
  2. `eval_runner.score_case` 在 category 为 `tool_choice / skill_route / subagent_delegate` 时找不到 key，统统返回 0。
  3. 阈值 `0.10 / -0.05` 硬编码，不可配置。
     位置：[backend/tars/evolution/eval_runner.py:61-62](../../backend/tars/evolution/eval_runner.py#L61-L62)
  4. `ingest_turn` 不传 `skill_id`，eval gate `skill_route` 类永远 0 分。
     位置：[backend/tars/evolution/manager.py:137](../../backend/tars/evolution/manager.py#L137)
- **处理方式**：
  1. 把 EvalContext 扩展为 `{personality, prompt_overlay, skill_routes, subagent_weights}`；orchestrator before/after 各自快照填充。
  2. `score_case` 根据 category 走对应字段；缺失字段时跳过该 case 而不是计 0（避免压低 delta）。
  3. 阈值入 yaml：`evolution.yaml: eval_gate: {improve_min: 0.10, regress_max: -0.05}`。
  4. `ingest_turn` 增加 `skill_id` 参数（从 `SkillRouter` 当轮命中信息读），透传到 FeedbackCollector。
- **验证**：补 4 个 case 类别各 1 个回归 case；故意制造 prompt 写回但 personality 不变，断言 gate 仍能识别 prompt 路径退步。

### F-07 [Phase 2] Prompt 写回未限幅 — spec 风险措施落空

- **现象**：`apply_prompt` 直接 `write_text(content)` 覆盖整文件；`prompt_tuner._apply_suggestions` 末尾持续 append 重复段，无去重、无长度上限。
- **根因**：spec §八明确"限制 diff 幅度；仅 append tuning 段"，实际未实现。
  位置：[backend/tars/evolution/apply_engine.py:119](../../backend/tars/evolution/apply_engine.py#L119)
- **处理方式**：
  1. 用 marker 块：`<!-- tars-evolution: tuned -->...<!-- /tars-evolution -->`，apply 时只替换 marker 内内容。
  2. 写入前检查 marker 块字数 ≤ 配置上限（默认 800 字），超过则丢弃本次写回 + audit `prompt_diff_too_large`。
  3. PromptTuner `_apply_suggestions` 内部去重（按 suggestion id）。
- **验证**：单测 - 100 次 optimize 后 prompt 文件大小不增长且 marker 块仍唯一。

### F-08 [Phase 2] Rollback 一致性弱

- **现象**：
  1. rollback 不校验当前文件 hash 是否等于 `after_hash`，会**静默覆盖未跟踪的修改**。
     位置：[backend/tars/evolution/apply_engine.py:208](../../backend/tars/evolution/apply_engine.py#L208)
  2. orchestrator 只 rollback `apply_records[-1]`，而一次 optimize 可能写回 personality + subagent + 6 个 prompt + 多个 skill。spec 说"rollback 最近一次 batch"。
     位置：[backend/tars/evolution/orchestrator.py:133](../../backend/tars/evolution/orchestrator.py#L133)
- **处理方式**：
  1. `ApplyEngine.rollback(apply_id)` 写回前先 `sha256(current_content) == after_hash` 校验，不一致则抛 `RollbackConflictError`，由 orchestrator 决定 force 或跳过。
  2. 引入 `batch_id`：每次 `apply_all` 生成一个 `batch_id`，所有 `evolution_apply_log` 写入该 batch_id；新增 `rollback_batch(batch_id)` 逆序回滚。
- **验证**：补 `test_rollback_detects_external_modification` / `test_rollback_batch_unwinds_all_records`。

### F-09 [Phase 2] Insight 集中窗口加速触发未实现

- **现象**：spec §3.3 trigger 3「Insight 👎 7 天内同 metric ≥3 次 → 加速触发」未实现，只在 `feedback_collector.record_insight_feedback` 入队，orchestrator 无窗口逻辑。
- **处理方式**：
  1. orchestrator 新增 `_check_insight_burst(tenant_id)`：query `evolution_events where source='insight' and signal='metric_downvote' and payload.metric_id=X and created_at > now()-7d`，count ≥3 → 触发 `optimize(reason="insight_burst", scope=["prompt","skill"])`。
  2. `Agent.ingest_turn` 之外加一个 cron-style 调度（复用 evolution_manager 心跳）。
- **验证**：单测 seed 3 条 insight downvote → orchestrator.optimize 被调一次。

### F-10 [Phase 2] `ingest_turn` 同步阻塞 + PromptCache 失效未实现

- **现象**：每 turn 同步写 JSON state，每 50 turn 同步触发 LLM × 6 + 文件 IO，可能造成单 turn 大延迟；`apply_all` 后未失效 PromptCache。
- **处理方式**：
  1. `ingest_turn` 末尾的 optimize 触发改为 `asyncio.create_task`（fire-and-forget + lock 防并发）。
  2. `_save_state` 改为节流（每 N turn 或 5s 一次）。
  3. `ApplyEngine.apply_all` 完成后调 `prompt_cache.invalidate(tenant_id=...)`（如目前无 PromptCache，留 TODO + spec 注脚）。
- **验证**：基准测试 - 50 turn loop 末尾 turn 延迟与 p50 差距 < 200ms。

### F-11 [Phase 3] Follow-up Queue drain race

- **现象**：`mark_idle` 与 drain 第一次 `mark_busy` 之间，新到达的 WS 消息可 `try_acquire` 成功并启动并发 turn，导致同 session 同时跑两个 `_execute_agent_turn`。
- **根因**：`router.py:78` 用 `asyncio.create_task(dispatch(data))` 并发调度入站；`websocket.py:96-98` 在 finally 中先 `mark_idle` 再 `_drain_follow_up_queue`。
  位置：[backend/tars/channels/websocket.py:96-98](../../backend/tars/channels/websocket.py#L96-L98)
- **处理方式**：
  1. drain 内部 loop 把当前会话视作仍占用：在 drain 完成前不调 `mark_idle`。
  2. 或者 `try_acquire` 增加 `if queue.has_pending(): return False`，强制走入队路径。
- **验证**：补 `test_follow_up_queue_no_concurrent_turns`：mock 长 turn，drain 中再发消息，断言不会同时执行。

### F-12 [Phase 3] outbound 仍散点直调 connection_manager

- **现象**：设计原话「所有 outbound 事件经 channel.send，禁止 scattered connection_manager 直调」，但实际 5+ 处仍直调：
  - `agent/agent.py:1069`
  - `cron/runtime.py:111/123/138`
  - `cron/executors/prompt.py:33`
  - `security/approval_service.py:125`
- **处理方式**：
  1. 把 `connection_manager.send_personal_message` 调用替换为 `channel_router.send(channel="websocket", session_id=..., event=...)`。
  2. 短期：`channels-architecture.md` 加一节「渐进迁移残留点清单」，列明上述 5 处与目标版本（v4.4）。
- **验证**：grep `connection_manager.send` 出现次数监控（v4.4 应为 0）；现存测试不变。

### F-13 [Phase 3] Cron prompt 缺 session_id 静默 fallback

- **现象**：spec §六明确「prompt cron 无 session_id → job 标记 failed，不 crash scheduler」，实际静默 fallback 到 `"default"` 会污染默认会话。
  位置：[backend/tars/cron/executors/prompt.py:55](../../backend/tars/cron/executors/prompt.py#L55)

- **验证**：单测断言无 session_id 时 job last_run='failed'，且不抛异常。

### F-14 [Phase 1] meeting_collection_prefixes 当作 collection_id 直查

- **现象**：默认配置 `prefix="meeting"`，实际只会命中名为 `"meeting"` 的单个 collection，无法按前缀枚举多个会议库。
  位置：[backend/tars/insight/knowledge_bridge.py:92-100](../../backend/tars/insight/knowledge_bridge.py#L92-L100)
- **处理方式**：
  1. 调用 `knowledge_store.list_collections(tenant_id)` 获取全量 collection_id；filter `id.startswith(prefix)`。
  2. 对 filter 后的每个 collection 各 `search_knowledge`，结果合并 + dedupe。
  3. 加缓存（list_collections 60s TTL）避免每次 ask 全表扫。
- **验证**：单测 seed 三个 `meeting_a/b/c` collection，bridge 三个都被检索。

### F-15 [Phase 1] adopt 同步阻塞 publish_metric_card

- **现象**：adopt 路径同步调用包含索引重建的 publish，可能阻塞几百 ms~s。spec §3.2 描述是"不阻塞 adopt"。
  位置：[backend/tars/insight/adoption_service.py:79-105](../../backend/tars/insight/adoption_service.py#L79-L105)
- **处理方式**：FastAPI 路由层加 `BackgroundTasks.add_task(self._publish_async, metric)`；adopt 立即返回；publish 失败仍写 `knowledge_publish_failed` 审计（不影响 adopt）。
- **验证**：基准测试 adopt p99 < 200ms。

### F-16 [Phase 1] search_docs_by_metric_id LIKE 通配符未转义

- **现象**：`metadata_json LIKE '%{metric_id}%'`；若 metric_id 含 `%/_` 会宽匹配甚至全表扫描。
  位置：[backend/tars/knowledge/sqlite_store.py:212-251](../../backend/tars/knowledge/sqlite_store.py#L212-L251)
- **处理方式**：
  1. 在 Python 层先校验 `metric_id` 仅含 `[A-Za-z0-9_-]`，否则 reject + log。
  2. SQL 改 `LIKE ? ESCAPE '\\'`，对 `%/_/\` 转义后再传入。
- **验证**：单测 metric_id `"%admin"` 应被 reject 而非匹配所有文档。

### F-17 [杂项] FastAPI version 字段未同步
