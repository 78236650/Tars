# TARS v3.9.1 — 登录页面设计文档

## 概述

当前前端已经具备基础认证能力，`auth store` 以 API Key 方式维护登录态，但应用主界面已经演进为带品牌风格的工作台壳层，并且设置页中已经出现用户管理入口。这说明登录入口不能再只是一个简陋表单，而需要承担三件事：

- 让用户第一眼知道这是 TARS，而不是普通后台系统
- 用统一入口同时承接管理员与普通成员
- 为后续工作区、多用户管理、邀请码加入、SSO 扩展预留空间

本轮登录页设计采用统一入口方案，围绕“账号 + 工作区”构建，并以品牌化双栏布局作为首屏结构。管理员和普通成员共用同一登录页面，登录后再根据角色与工作区上下文进入各自落地页。

**版本：** v3.9.1
**范围：** 前端登录页、登录卡片、加入工作区入口、登录后基础分流、错误提示
**非目标：** 本轮不实现 SSO、多因子认证、完整自助注册、复杂租户发现页

---

## 1. 设计目标

### 1.1 用户目标

- 管理员进入登录页后，能够清楚理解 TARS 支持团队管理、成员邀请和工作区协作。
- 普通成员进入登录页后，能够通过账号直接登录，并在需要时通过邀请码或加入入口进入工作区。
- 已登录用户访问登录页时，不会再次停留在登录表单，而是直接跳转回可用工作区或默认首页。

### 1.2 产品目标

- 登录页视觉上承接当前桌面工作台风格，而不是退回到传统后台系统样式。
- 统一入口优先，避免为管理员和成员分别设计两套完全不同的登录流程。
- 工作区作为重要上下文存在，但不抢占首屏主流程，不做“先选租户再登录”的重流程。
- 在不明显扩大实现复杂度的前提下，为未来 `SSO`、最近工作区、API Key 兼容入口等能力预留接口。

---

## 2. 方案选择

### 2.1 备选方向

本轮讨论过三种方向：

| 方案 | 结构 | 特点 |
|------|------|------|
| A | 品牌分栏 | 左侧讲产品与角色，右侧承接登录动作 |
| B | 工作区优先 | 首屏先找工作区，再进入账号登录 |
| C | 紧凑门户 | 只保留最基础登录表单与少量辅助入口 |

### 2.2 最终选择

最终采用 **方案 A：品牌分栏**。

选择理由：

- TARS 当前定位更接近“AI 工作台 / Agent 操作台”，而不是“以租户查找为核心的企业门户”。
- 现有主应用 `DesktopShell.vue` 已经具备明显的品牌壳层和工作台气质，登录页需要与其风格连续。
- 统一入口是已确认需求，方案 A 最适合同时表达“管理”和“使用”两个场景。
- 方案 A 更容易自然承接 `加入工作区`、`最近工作区`、`SSO` 等后续增强能力，而不会让首屏流程过重。

不采用的原因：

- 不采用方案 B，因为它会过早把用户注意力放到“找团队/找租户”，削弱 TARS 的品牌识别和产品能力认知。
- 不采用方案 C，因为它虽然最轻，但承载不了“多用户管理和使用”的产品叙事。

---

## 3. 页面结构

### 3.1 总体布局

登录页采用双栏结构：

- 左侧为品牌与角色说明区
- 右侧为登录卡片区

整体目标是让用户在一个屏内同时完成以下认知：

1. 这是 TARS
2. 它支持团队协作和多用户管理
3. 我现在可以登录，或者加入工作区

### 3.2 左侧品牌区

左侧区域承接品牌和产品定位，不承担实际登录操作。

展示内容包括：

- 产品 Logo
- 产品标题，例如“你的团队 AI 工作台”
- 一段简明价值说明，覆盖聊天、记忆、工具、知识库、会议等核心能力
- 管理员与成员的角色说明卡片
- 多用户协作、工作区隔离、统一身份入口等能力标签

左侧的作用不是做营销页面，而是建立可信感和角色认知，避免用户把登录页理解成纯表单。

### 3.3 右侧登录卡片

右侧区域是唯一主操作区，负责所有认证和加入动作。

结构如下：

- 卡片标题：欢迎回来 / 登录到工作区
- 主字段：`邮箱 / 用户名`
- 主字段：`密码`
- 辅助字段：`工作区名称（可选）/ 邀请码`
- 主按钮：`登录并进入`
- 次级入口：`加入工作区`
- 次级入口：`忘记密码`
- 底部扩展说明：可承接后续 `最近工作区`、`SSO`、`API Key` 兼容入口

设计原则：

- 登录页只有一个主按钮，避免首屏出现多个等权重主操作
- 工作区作为增强定位信息出现，不单独拆成第一步流程
- 新成员加入入口与登录入口并列，但视觉权重低于登录主动作

## 4. 登录与加入流程

### 4.1 登录流程

标准登录流程如下：

1. 用户输入用户名或邮箱
2. 用户输入密码
3. 用户可选填写工作区名称或邀请码
4. 点击 `登录并进入`
5. 认证成功后根据工作区上下文和角色信息决定跳转目标

### 4.2 工作区规则

工作区字段不作为必填项，但会影响登录后的目标定位：

- 如果用户填写了工作区名称或邀请码，则优先进入指定工作区
- 如果用户未填写，但存在最近访问的工作区，则优先回到最近工作区
- 如果用户既未填写也没有最近工作区，则进入默认首页或默认工作台入口

这样既能兼顾多工作区场景，又不会把首屏流程复杂化。

### 4.3 加入工作区流程

`加入工作区` 不跳转到独立页面，而是在登录页右侧卡片内展开轻量辅助流程。

建议支持两条路径：

- 通过邀请码加入
- 联系管理员获取邀请

本轮不做开放注册，也不做完整的工作区发现页。

### 4.4 忘记密码

`忘记密码` 作为次级入口存在，位于登录卡片底部，与 `加入工作区` 同级，但优先级略低于登录主按钮。

---

## 5. 登录后分流

### 5.1 统一入口，登录后分流

管理员和成员使用同一个登录页，不在首屏强制做角色选择。

登录成功后的落地规则：

- 管理员：进入同一主应用，但首屏默认落点更偏向管理入口，如设置、成员管理或工作区总览
- 普通成员：进入自己的默认工作区主页，优先回到聊天页或最近使用模块

### 5.2 已登录访问登录页

如果用户已经处于有效登录态，再访问登录页时应直接跳转，不再展示表单。

跳转优先级建议为：

1. 指定工作区
2. 最近工作区
3. 默认首页

---

## 6. 页面状态与错误处理

### 6.1 页面状态

登录页至少需要覆盖以下状态：

- 初始态
- 提交中
- 登录失败
- 加入工作区展开态
- 邀请校验失败
- 已登录自动跳转

这些状态都应在同一页面内完成，不采用多页面来回切换。

### 6.2 错误提示规则

错误信息必须贴近当前动作展示，不使用浏览器 `alert` 作为主交互方式。

建议规则如下：

- 密码错误：显示在登录卡片内部，靠近主按钮
- 工作区不存在：显示在工作区相关字段附近
- 邀请码无效：显示在加入工作区区域内部
- 网络错误：显示统一兜底提示，并允许重试

错误文案需要明确区分失败类型，避免所有问题都回落为“登录失败”。

## 7. 组件拆分

建议拆分为以下前端组件：

```text
frontend/src/views/LoginView.vue
frontend/src/components/auth/LoginHeroPanel.vue
frontend/src/components/auth/LoginCard.vue
frontend/src/components/auth/WorkspaceJoinPanel.vue
frontend/src/components/auth/AuthFeedbackAlert.vue
```

### 7.1 组件职责

| 组件 | 职责 |
|------|------|
| `LoginView` | 页面容器，负责布局、路由守卫结果承接、整体状态管理 |
| `LoginHeroPanel` | 左侧品牌与角色说明区 |
| `LoginCard` | 登录字段收集、主提交动作、基础错误展示 |
| `WorkspaceJoinPanel` | 邀请码加入与加入工作区辅助流程 |
| `AuthFeedbackAlert` | 卡片内部的状态与错误提示展示 |

### 7.2 数据边界

- `auth store` 负责认证结果、用户信息和登录态维护
- 工作区名称解析、邀请码解析作为独立逻辑，不与基础认证方法强耦合
- 跳转规则由页面容器或路由层统一处理，不分散在多个子组件中

这样可以避免把所有登录逻辑都塞进单一 `login()` 方法中，降低后续扩展成本。

---

## 8. 与现有系统的衔接

### 8.1 现有前端上下文

当前项目已经具备以下基础：

- `frontend/src/stores/auth.ts` 已有登录态、当前用户和初始化认证逻辑
- `frontend/src/router/index.ts` 已有主应用路由，但尚未形成登录页路由守卫体系
- `frontend/src/components/layout/DesktopShell.vue` 已是品牌化工作台壳层
- `frontend/src/components/settings/UserSettings.vue` 已体现出多用户管理场景

这意味着登录页设计应以“扩展现有认证入口”为目标，而不是推翻当前壳层结构。

### 8.2 衔接策略

- 前端先从现有 `auth store` 演进，补充账号登录与跳转规则
- 登录成功后进入当前工作台壳层，而不是新增第二套应用容器
- 工作区字段先作为 UI 和路由上下文存在，后续再与真实工作区后端能力对齐

---

## 9. 测试建议

本轮优先覆盖以下四类场景：

- 成功登录
- 错误凭证提示
- 加入工作区流程展开与收起
- 已登录用户访问登录页自动跳转

不建议本轮优先投入：

- 大量视觉快照测试
- 复杂多角色端到端矩阵
- SSO 或多因子认证相关测试

测试目标应聚焦“入口是否可用”和“状态切换是否清晰”，而不是一次性覆盖未来所有扩展场景。

## 10. 实施范围

### 10.1 本期范围

- 新增统一登录页
- 实现双栏布局与品牌信息区
- 实现登录卡片主流程
- 实现加入工作区入口与基础展开逻辑
- 实现登录失败与加入失败的卡片内提示
- 实现已登录自动跳转和基础角色分流

### 10.2 不在本期范围

- 企业 SSO
- 多因子认证
- 最近工作区切换器
- 完整自助注册
- 独立租户发现页
- API Key 与账号登录双入口并列呈现

---

## 11. 实施顺序

1. 新增登录页路由与未登录入口
2. 抽离登录页容器与左右区域组件
3. 接入基础账号登录提交流程
4. 增加加入工作区展开区域
5. 接入登录后跳转与已登录重定向
6. 完善错误提示与状态切换
7. 补齐相关前端测试

---

## 12. 结论

本轮登录页设计以“统一入口、多用户协作、品牌化承接”为核心，最终选择品牌分栏结构：

- 左侧负责建立 TARS 的产品认知和角色认知
- 右侧负责承接登录、加入工作区和找回密码等动作
- 管理员与成员共用入口，登录后再根据上下文分流
- 工作区作为重要上下文保留在登录卡片中，但不升级为前置重流程

该方案既符合当前 TARS 的产品定位，也能在较低复杂度下为未来多工作区和企业接入能力留下扩展空间。
