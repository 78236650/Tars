# TARS v3.9.1 — 默认管理员账号自举设计文档

## 概述

当前登录链路已经从纯 API Key 模式扩展为“用户名/邮箱 + 密码”登录，但系统仍缺少一个关键的自举能力：首次启动或缺少管理员账号时，用户无法直接用账号密码进入系统。

为了解决“系统可登录入口不存在”的问题，本次设计引入一个最小且明确的默认管理员账号自举逻辑：

- 服务启动时检查当前系统中是否存在任意管理员账号
- 如果不存在，则自动创建一个固定默认管理员
- 如果已存在管理员，则不做任何写入

本设计的目标不是实现完整的安装向导或生产级初始化系统，而是在当前阶段提供一个可预期、可测试、可回退的管理员兜底入口。

**版本：** v3.9.1
**范围：** 后端默认管理员自举逻辑、登录可用性、对应测试
**非目标：** 环境变量注入管理员、首次登录强制改密、重置密码、邀请制初始化、安装向导

---

## 1. 设计目标

### 1.1 用户目标

- 在一个全新或没有管理员的系统中，用户可以直接使用默认管理员账号登录。
- 不需要额外手工写库、改代码或调用接口来初始化第一个管理员。
- 如果系统已经存在管理员，不会因重启服务而被额外插入第二个默认管理员。

### 1.2 系统目标

- 尽量复用现有 `UserStore`、密码哈希与登录接口，不引入第二套初始化链路。
- 保证逻辑边界清晰：这是一段“启动兜底自举”逻辑，不是长期权限管理方案。
- 在最小改动范围内，确保默认管理员可被正常登录接口识别和使用。

---

## 2. 方案选择

### 2.1 备选方案

| 方案 | 规则 | 优缺点 |
|------|------|--------|
| A | 只要系统中没有管理员，就自动创建默认管理员 | 最能解决“系统不可登录”问题，适合当前阶段 |
| B | 只有用户表为空时才自动创建默认管理员 | 更保守，但库里已有普通用户时仍可能没有管理员入口 |
| C | 每次启动都确保默认管理员存在 | 最稳，但会把首次初始化与运行期修复混在一起 |

### 2.2 最终选择

采用 **方案 A**。

选择原因：

- 当前核心问题是“系统没有可登录管理员”，而不是“系统第一次启动时是否为空库”。
- 只判断是否存在管理员，比判断“是否空库”更符合真实问题。
- 只要系统中已经有管理员，就完全不插手，避免破坏现有账号体系。

不采用的原因：

- 不采用方案 B，因为它会漏掉“已有普通用户但没有管理员”的异常状态。
- 不采用方案 C，因为它会让“首次初始化”与“日常运行修复”耦合，边界不够清晰。

---

## 3. 默认管理员规则

### 3.1 触发时机

默认管理员自举逻辑放在后端应用启动阶段执行，靠近 `startup` 生命周期，而不是前端入口或一次性脚本。

### 3.2 判断条件

启动时读取当前用户列表：

- 如果存在任意 `role=admin` 用户，则直接返回，不创建默认管理员
- 如果不存在任何管理员，则进入默认管理员创建逻辑

### 3.3 默认凭据

默认管理员账号固定为：

- 用户名：`admin`
- 邮箱：`admin@tars.local`
- 密码：`Admin123!`

该密码只作为本地开发与首次自举用途，后续应补充修改密码能力。

---

## 4. 冲突处理

### 4.1 邮箱冲突

如果系统中不存在管理员，但 `admin@tars.local` 已经被普通用户占用：

- 不自动覆盖该用户角色
- 不自动修改该用户密码
- 记录启动警告
- 跳过默认管理员创建

原因：不能在没有显式授权的情况下，偷偷将现有普通用户提升为管理员。

### 4.2 用户名冲突

如果系统中不存在管理员，但用户名 `admin` 已被非管理员用户占用：

- 不自动接管该用户名
- 记录启动警告
- 跳过默认管理员创建

### 4.3 重复启动

只要默认管理员或任何其他管理员已经存在，后续重启都不应再创建新的默认管理员，确保该逻辑天然幂等。

---

## 5. 实现边界

### 5.1 放置位置

建议在 `backend/tars/main.py` 的启动阶段新增一个小函数，例如：

```python
def ensure_default_admin():
    ...
```

该函数只负责：

- 查询当前用户
- 判断是否已有管理员
- 检查默认用户名/邮箱冲突
- 在安全条件下创建默认管理员

### 5.2 复用现有能力

默认管理员必须通过现有的 `user_store.create_user(...)` 创建，而不是手写 SQL。

原因：

- 可复用现有密码哈希逻辑
- 可复用现有用户模型与时间字段写入
- 降低与 `UserStore` 内部结构不一致的风险

### 5.3 日志策略

启动时建议打印以下级别的日志：

- 成功创建默认管理员：打印用户名和邮箱，不打印明文密码
- 因已有管理员跳过：可打印简短调试信息
- 因用户名/邮箱冲突跳过：打印明确警告，方便定位

---

## 6. 测试设计

本轮重点覆盖以下行为：

### 6.1 自动创建

- 当系统中没有任何管理员时，启动逻辑会创建一个默认管理员

### 6.2 不重复创建

- 当系统中已经存在管理员时，启动逻辑不会重复创建第二个默认管理员

### 6.3 非空库补管理员

- 当系统中已有普通用户但没有管理员时，启动逻辑仍会补一个默认管理员

### 6.4 登录可用

- 自动创建出的默认管理员可以通过现有 `/api/auth/login` 接口使用默认密码登录

### 6.5 冲突跳过

- 当默认用户名或邮箱被非管理员占用时，不会自动篡改现有用户，也不会错误创建第二个冲突账号

---

## 7. 风险与限制

### 7.1 安全性

固定默认密码不适合作为长期生产策略。

本次方案仅适合作为：

- 本地开发默认入口
- 首次自举兜底
- 缺少管理员时的最低可用保障

### 7.2 功能边界

本轮不解决：

- 默认管理员首次登录强制改密
- 修改密码
- 重置密码
- 通过环境变量自定义默认管理员凭据
- 通过安装向导创建首个管理员

### 7.3 冲突时不可自动修复

如果默认邮箱或用户名已被普通用户占用，本设计选择“安全跳过”而不是“自动提权修复”。

这是有意为之，目的是避免自动修改现有账号权限造成更大的安全和数据风险。

---

## 8. 实施顺序

1. 为默认管理员自举逻辑补后端失败测试
2. 在启动阶段新增 `ensure_default_admin()` 最小实现
3. 复用现有 `create_user()` 完成默认管理员创建
4. 跑通“创建、跳过、登录”三类核心测试
5. 明确默认登录凭据文档与交付说明

---

## 9. 结论

本轮采用“只要系统中不存在管理员，就在启动时自动创建默认管理员”的方案。

默认管理员固定为：

- 用户名：`admin`
- 邮箱：`admin@tars.local`
- 密码：`Admin123!`

该方案以最小改动复用现有认证链路，能直接解决当前“系统没有可登录管理员账号”的问题，同时避免在已有管理员场景下重复写入或干扰现有账号体系。
