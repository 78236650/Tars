# TARS v3.9.1 — 前端中英双语完善设计文档

## 概述

当前前端已经具备基础的 `useI18n()` 能力和一份集中式 `messages` 词典，但页面级双语切换仍然不完整，主要存在以下问题：

- 同一个页面中混用了 `t(key)`、硬编码中文、硬编码英文和未注册 key。
- `router meta` 中的桌面标题与副标题直接写死为中文，导致切换语言后桌面头部不能同步切换。
- Toast、`confirm`、`alert`、前端拼装提示等“交互链路文案”没有统一走 i18n。
- 某些模块已局部接入 i18n，但词条组织零散，导致文案不精准或中英切换不彻底。

本轮目标不是引入新国际化框架，而是在现有实现上做一次“全量补齐 + 统一规范”，确保每个一级页面及其核心交互内容都能精准完成中英切换。

**版本：** v3.9.1
**范围：** 前端国际化词条、页面文案、桌面头部、弹窗提示、前端生成提示
**非目标：** 后端多语言返回、第三方库默认文案汉化/英化、SEO 多语言站点支持

---

## 1. 目标

### 1.1 用户目标

- 在任意页面切换语言后，页面标题、操作按钮、表单说明、空态、状态文案能立即同步切换。
- 在弹窗、Toast、确认框、抽屉等交互场景中，不再出现“页面切成英文但提示还是中文”的割裂感。
- 中英文文案都保持自然、准确、上下文一致，而不是简单逐字翻译。

### 1.2 设计目标

- 保留当前轻量级 `useI18n()` 架构，不引入 `vue-i18n` 级别的大迁移。
- 所有前端可控文案必须收口到 key，避免继续扩散硬编码字符串。
- 路由级标题和页面级正文使用统一词条体系，支持切换时实时更新。
- 优先保证“完整切换”与“文案准确”，其次再考虑词条拆分整理。

## 2. 范围定义

### 2.1 本轮纳入范围

按页面维度，本轮覆盖以下一级页面及其直接关联组件：

| 页面 | 主要范围 |
|------|----------|
| Chat | 会话列表、输入区、欢迎态、提醒入口、消息辅助状态文案 |
| Memory | 顶部统计、Tab、筛选、空态、记忆卡片、压缩与合并弹层 |
| Models | 模型页头部、Ollama 区、远端端点区、编辑弹层、提示反馈 |
| Tools | 工具页头部、Tab、SkillHub 搜索、安装反馈、工具详情、添加技能 |
| BI | 页面头部、数据源设置、Schema 标注、查询与结果状态 |
| Meeting | 页面容器、设置区、上传区、录音区、转录历史、详情区、删除/失败提示 |
| Knowledge | 页面头部、知识管理区、文档上传区、检索结果与空态 |
| Settings | 页面头部、Tab、用户管理、子代理设置、人格设置 |

按交互类型，本轮覆盖：

- 页面标题、副标题、导航名
- 按钮、标签、表单 label、placeholder、帮助说明
- 空态、加载态、状态 badge
- Toast 成功/失败提示
- `confirm` / `alert` 等前端确认提示
- 前端代码拼接生成的结果提示
- 桌面工作台头部标题、副标题、状态文案

### 2.2 本轮不纳入范围

- 后端接口直接返回的自由文本做全量多语言改造
- 浏览器原生时间、日期、数字格式的地区化格式适配
- Markdown 正文内容的自动翻译
- 用户上传内容、模型回复内容的翻译

## 3. 现状问题归类

### 3.1 词条层问题

- `frontend/src/i18n/index.ts` 已有基础词条，但覆盖范围明显不足。
- 存在直接调用 `t('back to chat')` 这类未注册 key 的情况，最终会回显原字符串。
- 中英文词条粒度不统一，有的以页面命名，有的以通用语义命名，后续维护成本高。

### 3.2 组件层问题

- 部分页面头部、局部按钮、说明文案仍直接写在模板中。
- 某些组件虽然引入了 `useI18n()`，但只替换了一部分文案。
- 同一个动作在多个组件中使用了不同的文案表达，切换后不一致。

### 3.3 壳层与路由问题

- `router/index.ts` 的 `desktopTitle` / `desktopSubtitle` 为中文常量。
- `DesktopShell.vue` 直接读取路由文本，无法在语言切换时通过 key 实时重算。
- 桌面头部中的 `Model`、`未选择模型`、跳转按钮等仍有硬编码。

### 3.4 提示链路问题

- Toast 中混用了 key、自由文本和接口原文。
- 删除确认、失败提示等直接写字符串，导致切换不完整。
- 某些提示由字符串拼接生成，例如“已拉取 N 个模型”，需要参数化而不是简单拼接。

## 4. 设计方案

### 4.1 方案选择

本轮采用“集中式补全并规范化”的方案：

- 继续保留单文件 `messages` 作为词条源。
- 补齐缺失 key，并统一 key 命名规则。
- 逐页替换硬编码文案，确保所有前端可控文案最终走 `t()`。
- 将路由 `meta` 中的展示文案改为 i18n key，由壳层组件实时翻译。

不采用的方案：

- 不在本轮引入 `vue-i18n`，避免带来额外依赖、API 迁移和测试面扩大。
- 不在本轮先做多文件词典拆分，避免“结构更漂亮但页面仍未补齐”的优先级倒置。

### 4.2 命名规则

词条命名采用“页面/模块前缀 + 语义字段”的方式，例如：

```text
desktop.chat.title
desktop.chat.subtitle
meeting.deleteFailed
settings.backToChat
modelsPage.fetchOk
```

规则说明：

- 页面头部统一使用 `desktop.*`
- 一级页面正文使用页面前缀，例如 `meeting.*`、`knowledge.*`
- 通用按钮保留在 `common.*`
- 模块内弹层或次级组件继续使用所属模块前缀，避免出现大量模糊通用 key

### 4.3 路由标题设计

`router/index.ts` 不再直接存中文展示文案，而是保存 key：

```ts
meta: {
  desktopTitleKey: 'desktop.chat.title',
  desktopSubtitleKey: 'desktop.chat.subtitle',
}
```

`DesktopShell.vue` 内部负责：

- 从当前路由 meta 读取 key
- 使用 `t()` 实时计算标题与副标题
- 为缺省情况提供统一 fallback key，而不是直接写死中文

这样切换语言后，桌面头部会立即同步，无需刷新页面。

### 4.4 页面组件改造策略

每个页面按以下顺序补齐：

1. 页面头部标题、副标题
2. Tab、筛选项、按钮、操作入口
3. 表单 label / placeholder / hint
4. 空态、加载态、状态 badge
5. Toast、`confirm`、`alert`、错误提示
6. 动态拼接提示改为参数化文案或模板化文案

页面内部如果存在多个子组件，由页面所属前缀统一命名，避免在不同组件里各起一套词条。

### 4.5 动态文案与参数设计

对带参数的文案，短期不引入复杂 message formatter，而是使用轻量模板替换能力。

建议在现有 `t()` 基础上扩展为：

```ts
t('modelsPage.fetchOk', { count: 3 })
```

典型场景包括：

- 拉取模型数量
- 安装成功后的数量或名称提示
- 删除对象名称确认
- 状态统计类说明

如果本轮不扩展参数能力，也必须保证相关拼接逻辑统一收敛为辅助方法，不能继续散落在组件里手写字符串拼接。

### 4.6 接口错误与前端提示边界

本轮只处理“前端可控错误文案”：

- 表单校验错误
- 操作失败兜底提示
- 常见确认提示
- 前端本地状态提示

对后端返回的自由文本错误，策略如下：

- 优先原样展示后端错误，避免误译导致信息失真
- 若是已知高频错误码或固定错误语句，可在前端做有限映射
- 不做一轮全量“错误信息翻译工程”

## 5. 文件与职责

### 5.1 词条源

核心文件：

```text
frontend/src/i18n/index.ts
```

职责：

- 保存 `zh` / `en` 双语词典
- 提供全局共享的 `locale`
- 提供 `t()`、`setLocale()`、`toggleLocale()`
- 提供必要的参数替换能力或轻量辅助能力

### 5.2 路由层

核心文件：

```text
frontend/src/router/index.ts
frontend/src/components/layout/DesktopShell.vue
```

职责：

- 路由层只保留文案 key，不保留最终展示文本
- 壳层负责将 key 转成当前语言文案
- 桌面头部所有静态文案统一接入 i18n

### 5.3 页面与组件层

页面与核心组件职责：

- 页面负责定义页面级词条语义
- 子组件复用页面前缀或模块前缀
- 不允许继续引入新的硬编码展示文案
- 新增或修改功能时，同步补词条，而不是事后回补

---

## 6. 实施顺序

为降低回归风险，按以下顺序推进：

1. 扩展和整理 `i18n/index.ts` 词条结构
2. 修正 `router meta`，把桌面标题改成 key
3. 改造 `DesktopShell`，完成头部实时翻译
4. 优先修复 `Settings`、`Models`、`Tools` 这类头部和交互链路明显的页面
5. 修复 `Meeting`、`Knowledge`、`BI` 等业务页面
6. 修复 `Memory` 与 `Chat` 的辅助提示和边角文案
7. 统一扫尾 `Toast`、`confirm`、`alert`、动态拼接提示
8. 补充测试并进行逐页手动回归

这样排序的原因：

- 先稳定基础设施，后逐页替换，避免页面改完后还要返工路由与壳层。
- 先处理问题最明显、覆盖面最大的头部和操作提示，尽快消除“切一半”的体验问题。
- 末尾统一清理提示链路，避免遗漏。

---

## 7. 测试策略

### 7.1 自动化测试

优先补充以下测试：

- `useI18n()` 的语言切换与 fallback 行为
- 带参数文案的渲染结果
- `DesktopShell` 根据路由 meta key 正确渲染标题、副标题
- 切换语言后桌面头部同步更新
- 关键页面至少各有一个“切换后文案变化”的代表性测试

测试重点是“行为正确”，不是把所有词条逐个断言一遍。

### 7.2 手动回归

逐页检查以下内容：

- 页面头部
- 按钮与操作入口
- Tab / 筛选 / 标签
- 输入框 placeholder 与帮助说明
- 空态 / 加载态 / 状态 badge
- Toast / confirm / alert
- 抽屉、弹窗、详情面板

回归页面范围：

- `/`
- `/memory`
- `/models`
- `/tools`
- `/bi`
- `/meeting`
- `/knowledge`
- `/settings/*`

### 7.3 验收口径

页面切到英文后，不应再看到明显遗留的中文硬编码；切回中文后，不应保留英文按钮、标题或提示。

## 8. 风险与控制

### 8.1 词条膨胀风险

风险：

- 一次性补全会新增较多词条，`i18n/index.ts` 继续变大。

控制：

- 本轮先保证覆盖完整与命名一致。
- 下一轮如有必要，再做按模块拆分，不与当前补齐任务绑定。

### 8.2 漏改风险

风险：

- 页面已切换，但弹窗、Toast 或 confirm 仍残留旧文案。

控制：

- 按“页面正文 + 交互链路”双清单逐页检查。
- 使用搜索硬编码中文/英文的方式做收尾排查。

### 8.3 参数文案风险

风险：

- 直接字符串拼接在中英文下语序不同，可能造成英文不自然。

控制：

- 对带数量、名称、状态的提示优先改为参数化词条。
- 不再继续散落手写 `prefix + count` 这类拼接。

### 8.4 测试噪音风险

风险：

- 如果为每个词条都写测试，会让测试变得冗长且维护成本高。

控制：

- 只覆盖切换机制、路由联动、代表性页面和关键提示链路。

---

## 9. 验收标准

- 所有一级页面的标题、副标题、主要操作入口都能在中英文间准确切换。
- `DesktopShell` 头部标题、副标题、模型状态区与跳转入口在切换语言后同步变化。
- 页面内核心交互文案，包括表单、空态、加载态、状态 badge、弹窗、Toast、确认提示，都能完成切换。
- 不再出现未注册 key 回显原文、页面局部残留硬编码中文/英文的明显问题。
- 自动化测试通过，且逐页手动回归完成。
