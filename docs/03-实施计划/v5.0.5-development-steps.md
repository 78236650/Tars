# TARS v5.0.5 开发步骤文档

> 把 [设计文档](../superpowers/plans/2026-06-07-tars-v5.0.5-security-hardening-design.md) 拆成可执行的开发步骤。
> 每项含：改动文件、代码要点、验证方法。

## 约定

- 每个批次独立成 PR，独立验证、独立可回滚。
- 每项改动后跑：`cd backend && .venv/bin/python -m py_compile <改动文件>` + 相关测试。
- 前端改动跑：`cd frontend && npx vue-tsc --noEmit`（只看本次改动文件零错误）。
- 改动编号对应设计文档（S=安全，P=生产，A=Agent 能力）。

## 批次一：安全硬阻塞

### S1. skills.py 端点认证

**改动文件**：`backend/tars/api/skills.py`

**步骤**：
1. 确认 import：`from ._auth import require_authenticated_user, require_admin, require_module, Principal`、`from fastapi import Depends`。
2. 在 router 定义后加全局依赖：
   ```python
   router = APIRouter(prefix="/api/skills", tags=["skills"])
   router.dependencies = [Depends(require_module("skills"))]
   ```
3. 系统级端点（`reload`、DELETE `/{skill_id}`）函数签名追加 `principal: Principal = Depends(require_admin)`。
4. 移除原本逐端点重复的 require_authenticated_user（全局已覆盖，避免双重依赖）。

**验证**：
- `curl -X POST localhost:8000/api/skills/reload` 无 token → 401。
- 普通用户 token 调 `reload` → 403；admin token → 200。
- 跑 `pytest tests/ -k skill`（若有）。

### S2. 清理 knowledge 残留引用

**改动文件**：`api/knowledge.py`、`api/meeting.py`、`agent/prompt_builder.py`、`memory/turn_knowledge_publisher.py`、`main.py`

**步骤**：
1. **api/knowledge.py**：确认前端已无 `/api/knowledge/*` 调用（git 已删 knowledge 前端组件）。删除该路由文件，并移除 main.py 中 `include_router` 的挂载与 import。若需保留 URL 兼容，改为返回 410 Gone 的 stub router。
2. **api/meeting.py:832**：移除 `from ..knowledge.schema import ensure_knowledge_schema`。检查 `_ensure_meeting_collection()`（约 836 行）——若依赖该 schema，改用 WikiStore（894 行已 import）或直接走 database 表。
3. **agent/prompt_builder.py:208**：移除 `from ..knowledge.access import search_knowledge`。该处若是 prompt 注入知识检索结果，改为走 wiki 检索或删除该增强分支。
4. **memory/turn_knowledge_publisher.py**：移除条件 import 的 knowledge 兜底分支（v5.0.4 双向链接已用 wiki，此处是遗留兜底）。
5. **预部署校验**：新建 `scripts/check_imports.py`，遍历 import 所有 `api/*.py`，CI 跑一次。

**验证**：
- `grep -rn "from.*knowledge\.\|import.*tars\.knowledge" backend/tars/ --include="*.py"` 仅剩 insight 模块的 knowledge_bridge（不同模块，保留）。
- `.venv/bin/python scripts/check_imports.py` 全绿。
- 手测：发起 meeting 转存、触发 kb_promotion，不再 ModuleNotFoundError。

### S3. 工具沙箱绝对路径拦截

**改动文件**：`tools/builtin/shell.py`、`tools/builtin/python_exec.py`、`tools/dispatcher.py`

**步骤**：
1. **shell.py**：加 `_validate_command_path_safety(command, allowed_dirs)`，正则拦截访问 workspace 外绝对路径（`cat/less/cd/> /etc|/usr|/var|/root` 等），execute() 开头校验，命中返回 error。
2. **python_exec.py**：构造受限 globals，覆写 `open` 校验绝对路径在 allowed_dirs 内；危险 import（subprocess/os.system）告警或拒绝。
3. **dispatcher.py**（约 198-209）：高危工具（shell/python_exec/file_write）fail-closed——`tenant_workspace_manager` 不可用时直接返回 error，不放行。

**验证**：
- shell 工具执行 `cat /etc/passwd` → 被拒。
- python_exec 执行 `open('/etc/passwd')` → PermissionError。
- workspace 内正常文件操作不受影响（回归测试）。

### S4. 认证失败接入审计日志

**改动文件**：`api/_auth.py`

**步骤**：
1. import `safe_audit` / audit_logger（fail-safe 包裹）。
2. `_principal_from_jwt`、`_principal_from_api_key`、`resolve_authenticated_principal` 各 40x 抛出前调 `log_login(success=False, reason=...)` 或 `log_permission_denied(...)`。
3. `require_admin`、`require_module` 的 403 前同样记录。
4. 全部审计调用用 try/except 包裹，审计失败不阻断认证。

**验证**：
- 无效 token 请求后，audit_logs 表出现 failed-auth 记录。
- 审计组件故意置 None，认证主流程仍正常 401（不因审计崩）。

### S5. 移除硬编码密钥

**改动文件**：`main.py`、`gateway/jwt_auth.py`、`Dockerfile.backend`、`deploy/.env.example`

**步骤**：
1. main.py 移除 `DEFAULT_ADMIN_PASSWORD='Admin123!'`，改为读 `TARS_ADMIN_PASSWORD` 环境变量；缺失时生成随机一次性密码并打印到启动日志（仅首次初始化）。
2. jwt_auth.py 生产环境缺 `TARS_JWT_SECRET` 时 fail-fast（补全已有逻辑）。
3. Dockerfile.backend 加 Docker secrets 挂载支持。
4. .env.example 用强随机占位值 + 注释说明必填。

**验证**：
- 源码 `grep -rn "Admin123\|password.*=.*['\"]" backend/tars/main.py` 无硬编码。
- 不设 TARS_JWT_SECRET 启动（生产模式）→ fail-fast 报错。

### S6. REST 限流接线 + 请求体上限

**改动文件**：`api/invoke.py`、`api/audit.py`、`api/memory.py`、`main.py`

**步骤**：
1. 把 `gateway/rate_limit.py` 的 RateLimiter 接入 invoke.py 等写入端点（依赖注入或中间件）。
2. audit.py 查询参数加 `max_length`（action 255、action_group 64、user_id 255、resource_type 128）。
3. memory.py Pydantic 模型加 `max_length`（UpdateCoreBlock 10000、UpdateMemory 100000、MemoryImport 5MB）。
4. main.py 加全局 RequestValidationError 处理器返回 422。

**验证**：
- 超长 action 查询 → 422。
- 高频调 invoke → 触发 429。
- 超大 import body → 422 而非 502。

## 批次二：生产就绪

### P1. 结构化日志框架
**改动文件**：新建 `tars/logging/__init__.py`、`tars/logging/config.py`；`main.py`；按模块迁移 `print()`。
**步骤**：
1. `logging/config.py` 写 `setup_logging(level, json_mode)`，用 dictConfig 配置 Formatter（`%(asctime)s %(levelname)s %(name)s %(message)s`）+ trace_id 注入。
2. main.py 启动期最先调 `setup_logging()`。
3. 按优先级迁移 print：`agent/` → `tools/` → `memory/` → `api/`。每文件 `logger = logging.getLogger(__name__)`，print 改 `logger.info/warning/error`。
4. 保留 `[Startup]` 类启动期 print（或一并迁移到 logger.info）。
**验证**：启动日志带统一格式与级别；`grep -rn "print(" backend/tars/agent backend/tars/tools` 显著下降。

### P2. 全链路 trace_id
**改动文件**：`tenant/context.py`、新建 `middleware/trace.py`、`main.py`、`logging/config.py`、`security/audit.py`、`tools/dispatcher.py`。
**步骤**：
1. context.py 加 `trace_id_var: ContextVar[str]` + get/set 辅助。
2. trace.py 写 `TraceIDMiddleware`：读 `X-Trace-ID` 头或生成 UUID（注意：脚本里不可用 Date/random，但运行时代码可用 `uuid.uuid4()`），set 到 ContextVar，写回响应头。
3. main.py 注册中间件，顺序在 UserContextMiddleware 之前。
4. 日志 Formatter 注入 trace_id；审计日志、dispatcher context 带上 trace_id。
**验证**：单次请求的所有日志行含同一 trace_id；响应头有 X-Trace-ID。

### P3. metrics 导出
**改动文件**：`requirements.txt`（加 prometheus-client）、新建 `middleware/metrics.py`、`main.py`、`tools/dispatcher.py`、`database/repositories/`（provider_usage 聚合）。
**步骤**：
1. 定义 Counter/Histogram（http 请求、工具耗时、token）。
2. FastAPI 中间件埋点；dispatcher execute 埋工具耗时。
3. provider_usage 加 `SUM/GROUP BY` 聚合查询 + `/api/metrics/provider/summary`。
4. 暴露 `/metrics` 端点（admin 或内网）。
**验证**：`curl /metrics` 返回 Prometheus 格式；调用后计数器增长。

### P4. 备份与迁移版本管理
**改动文件**：新建 `database/schema_versions.py`、`database/migrations/`、`scripts/backup.py`；`api/admin.py`。
**步骤**：
1. 建 `schema_versions` 表（version, checksum, applied_at）。
2. 把现有散落的 `ALTER TABLE` 整理为版本化迁移文件（`001_*.sql` 起），写 `apply_migrations()` 启动时按序应用并记录。
3. `scripts/backup.py`：SQLite 原子拷贝 + 压缩；PG 走 pg_dump。
4. admin 加 `POST /api/admin/backup`（require_admin）。
5. 写灾难恢复 runbook（含 RTO/RPO）到 `04-运维文档/`。
**验证**：迁移幂等（重复启动不报错）；备份脚本产出可还原文件；dry-run 校验。

### P5. 优雅关闭
**改动文件**：`lifespan.py`、`channels/websocket.py`、`main.py`。
**步骤**：
1. lifespan run_shutdown 加全局在途任务超时等待（`asyncio.wait_for(..., timeout)`）。
2. ConnectionManager 加 `async disconnect_all(timeout)`，遍历活跃连接发关闭帧。
3. main.py 注册 SIGTERM/SIGINT handler 调 shutdown；uvicorn 显式 `timeout_keep_alive`。
**验证**：发 SIGTERM 后在途请求完成再退出；WebSocket 收到关闭帧。

### P6. API key 加密 + 错误响应统一
**改动文件**：`database/`（api_key 列加密）、新建 `api/schemas.py`、`main.py`。
**步骤**：
1. user.api_key 加密存储（迁移脚本转换存量）。
2. schemas.py 定义 `ApiResponse`/`ApiErrorResponse`/`ErrorDetail`。
3. main.py 加全局 `@app.exception_handler(HTTPException)`，输出统一结构 + 错误码 + trace_id。
4. 响应包装向后兼容，逐端点迁移（不阻塞本版）。
**验证**：错误响应为统一结构；现有前端不因格式变化报错（兼容期）。

## 批次三：Agent 能力增强

> 工作量大，按需排期；每项独立 PR。

### A1. 工具循环超时与上下文控制
**文件**：`tools/dispatcher.py`、`agent/agent.py`。
- 工具结果超阈值（如 8K）截断+标记；`max_rounds` 默认 10（可配）。
- dispatcher 对单工具加 `asyncio.wait_for` 兜底超时；ToolResult 加 `recoverable`/`retry_suggested`。
- prompt fallback JSON 解析改多趟+校验+失败追问。
- 累计 token 超 context 70% 时摘要早期消息。
**验证**：长任务不再上下文溢出；本地模型工具解析失败率下降。

### A2. 审批闸可靠性
**文件**：`security/approval_service.py`、`tools/dispatcher.py`、`api/approvals.py`。
- timeout vs denied 返回不同信号；审批状态持久化到 DB。
- 超时前提醒 + 宽限窗口迟到审批恢复；加审批状态查询端点。
**验证**：进程重启后待审批可恢复；agent 能区分超时与拒绝。

### A3. 记忆系统降级
**文件**：`memory/reflector.py`、`memory/search.py`。
- Reflector 三层降级（LLM→Heuristic→最小归档）。
- HybridSearch 向量失败回退确定性 embedding；FTS 动态评分；暴露 fallback_depth。
**验证**：LLM 不可用时记忆仍写入；向量库宕机时搜索仍返回合理结果。

### A4. Agent 取消与后台任务生命周期
**文件**：`agent/agent.py`。
- 维护 `session_id -> [Task]`；`_abort_if_cancelled` 取消该会话后台任务；finally 清理。
**验证**：取消会话后后台反思/场景分析停止；连接不泄漏。

### A5. 并发编排防护
**文件**：`orchestration/orchestration_memory.py`、`agent/subagent_manager.py`、`orchestration/multi_agent_orchestrator.py`。
- per-task 锁保护并发文件写；编排前 DAG 循环依赖检测；多步操作事务包裹。
**验证**：并发子 agent 写同一 workspace 不损坏；循环依赖被拒绝。

### A6. Agent 决策可追溯
**文件**：`database/`（新建 agent_decisions 表）、`agent/agent.py`、`api/audit.py`。
- 记录技能路由/记忆检索/升格决策（含 trace_id）；查询端点 `/api/audit/decisions?trace_id=`。
**验证**：可按 trace_id 查回完整决策链。

### A7. 其他 medium（择机）
- execution_policy reload 端点；rate limiter pool 隔离+优先级；dead_letters 处理器（重试+告警+重放）；cron 任务超时保护；缓存多 worker 文档说明。

- 批次一全部合入且验证通过 → 平台通过基础安全审计。
- 批次二合入 → 具备生产可观测性与运维基建。
- 批次三按排期推进 → Agent 可靠性达企业级。
- 每项改动：编译通过 + 相关测试通过 + 不破坏既有测试。
- VERSION.md / changelog / release-notes 同步更新到 v5.0.5。
